## 一、已定（已验证 / 待落地逐条注明）

### D1 · 当前规模用内存暴力检索，不引入 ANN

- **决策**：向量存 MySQL 文本列，启动/重建时加载为内存矩阵，检索做全量余弦；不接 HNSW、不接向量库。
- **依据**：本机实测（`docs/实验记录.md` §1.1）——1,000 块 1.18 ms、10,000 块 12.75 ms、100,000 块 132.79 ms，严格线性；288 块不到 1 ms。
- **备选**：pgvector HNSW、Milvus、Elasticsearch dense_vector。代价是运维面与召回率下降，在当前数据量上换不到延迟收益。
- **重评估触发**：单实例稳定超过 5 万块，或检索 P95 超过 200 ms，或需要多实例共享索引（内存快照无法跨实例同步）。

### D2 · 检索编排自研，框架不接管

- **决策**：双路召回、RRF 融合、并发闸门、降级、增量重建全部自己写；LangChain4j 只用于文档切分与新数据源接入。
- **依据**：这些逻辑已经实现并被测试覆盖（`MsdsFusionTest`、`MsdsSearchDegradeTest`、`ResilienceTest`），也是项目真正的深度；交给框架黑盒后，降级与权重都不可控。
- **备选**：Spring AI / LangChain4j 的 `EmbeddingStoreContentRetriever`。
- **重评估触发**：阶段 2.5 的四档对照中，框架在**同一 embedding、同一题集**下 Hit@5 与 P95 都明显更优，且能复现。只有那时才考虑换主路径。

### D3 · 混合检索用 RRF；权重必须随 embedding 模型切换

- **决策**：`score = Σ w_i / (k + rank_i)`，`k=10`，两路深度 50。权重不是常量：local-hash 用 `3:1`，bge-m3 用 `1:2`（保守可选 `1:1`）。
- **依据**：
  - `docs/实验记录.md` §1.2：local-hash 下纯字面 17/20、纯向量 6/20、1:1 只有 14/20、3:1 是 18/20；3:1 是窄峰。
  - §1.5（E4）：bge-m3 纯向量就 20/20、MRR 0.825，融合 3:1 反而降到 18/20、0.781；1:1 是 20/20 / 0.842，1:2 是 20/20 / 0.867（Hit@1 15/20），1:3 开始回落。
- **机制**：当一路明显更强时，弱的那一路的名次会污染融合结果。固定加权隐含「两路精度相近」的假设，换模型后这个假设不再成立。
- **备选**：等权 1:1、分数归一化后加权、学习排序、按模型族在代码里自动选权重。
- **重评估触发**：换 embedding 模型（包括 DashScope v4 → bge-m3 之外的任何切换）必须重跑 `MsdsEmbeddingCompareTest` 或 `MsdsRrfWeightSweepTest`；题集扩充到 100 题以上后也要复测，20 题时 1 题 = 5 个百分点。
- **已落地（2026-11-05）**：`MsdsRetrievalProperties` 增加 `semantic-literal-weight=1.0 / semantic-vector-weight=2.0`；`MsdsSearchService` 按 `MsdsVectorService#usesSemanticEmbedding()` 选档，`MsdsSemanticWeightTest` 用「只有字面路贡献」的场景锁定分数为 `1/(k+1)`，退回 3:1 会立即失败。本地哈希档仍是 3:1，默认运行配置（`hazmat.ai.enabled=false`）行为不变。

### D4 · MSDS 按 GB/T 16483 的 16 节切块，单节超 400 字再按段落切

- **决策**：章节是语义边界；表格整表保留；块前加 `[化学品名]` 前缀并重算 `text_hash`。
- **依据**：用户问题直接指向某一节（「误食」→ §4，「泄漏」→ §6）；前缀解决「§4 正文不出现试剂名」导致的召回失败。`MsdsChunkerTest` 覆盖切分规则。
- **400 这个数字没有被 E3 证实**：`docs/实验记录.md` §1.4 显示 200/400/800 三档在当前 18 份种子文件上产出完全相同的 288 块、指标也相同——因为所有章节都是单段落，`MAX_CHARS` 只在段落之间生效。所以 400 只是「512 token 模型的安全余量」，不是实测最优值；章节切分本身是已验证的，阈值不是。
- **备选**：固定 200/400 字切、递归字符切分、父子块。
- **重评估触发**：阶段 2 引入 PDF 抽取的多段落 SDS 后重跑 E3；若 200 字在 Hit@5 上明显更好，说明单节内信息太杂，应考虑按小节或句子切，而不是继续调 `MAX_CHARS`。另：真实 MSDS 出现单节远超 8192 token 时必须重新切。

### D5 · document + chunk 两表，块级 `textHash` 增量

- **决策**：不按文档类型分表；增量判据是 `(cas_no, text_hash)`，复用时保留向量与 `indexed_at`。
- **依据**：按块下标匹配会在文档中间插入一节后让后面每块错位、整篇重编；内容匹配只影响真正变了的块。现有 `reindex` 二次执行返回 `reused=288, created=0`。
- **备选**：按文档整篇重建、按 `(doc_id, seq)` 匹配。
- **重评估触发**：出现跨块的语义重复（同一条款在多个文档重复），需要去重或合并时，单靠 hash 不够。
- **落地（2026-11-06）**：V7 新增 `knowledge_document` 存文档元数据，`msds_chunk` 增加 `document_id` / `doc_type` / `clause_no` / `index_version`。三类知识源共用块表，增量判据仍是 `(cas_no, text_hash)`；非 MSDS 文档没有 CAS，`cas_no` 列填 `source_code` 以保持列非空。

### D6 · 并发闸门只保护向量路，不保护字面路

- **决策**：拿不到许可时跳过向量检索，字面照常返回，`degraded=true` 并说明原因；只有真正拿到许可才 `release()`。
- **依据**：2026-11-05 修复。原实现在许可耗尽时返回空列表，用户会误以为库里没有这条知识。字面路是纯内存扫描、无外部依赖，也是过载时唯一还能出结果的路径。
- **备选**：整体限流并返回 503；字面路也纳入闸门。
- **重评估触发**：字面路本身成为 CPU 瓶颈（库规模进入十万级且并发持续打满），需要重新评估是否给字面路单独限流。

### D7 · 内存索引在事务提交后构建

- **决策**：`rebuild()` 的 `TransactionTemplate.execute` 返回后，再从库里重建 `literalIndex`；事务回滚则保留旧索引。
- **依据**：2026-11-05 修复。原实现在事务内替换索引，回滚后内存索引会指向已回滚、库里不存在的「幽灵块」。
- **备选**：事务内构建、提交后再原子替换引用（当前实现更简单，多一次全表查询）。
- **重评估触发**：块数增长到全表查询不可忽略（十万级以上），改为「构建新索引 → 提交后原子替换」。

### D8 · 降级必须显式，共四条路径

- **决策**：无 key（local-hash）、查询 embedding 失败、向量路并发满、四元组不符，全部返回 `degraded` / `degradedReason` / `needsRebuild`，不静默退化。
- **依据**：静默退化会让用户以为「向量没帮上忙」，实际是「压根没跑」。四条路径都有测试覆盖。
- **备选**：统一返回 5xx 或空列表。
- **问答层（2026-11-06 补充）**：`/ask` 把「未启用生成模型」「模型调用失败」「模型明确拒答」「片段与问题没有词面对应」拆成独立状态，分别落进 `generated` / `answerable` / `degradedReason`，不合并成一个 `error`。最后一条是新增的拒答条件：本地哈希向量对任何查询都会返回若干命中，没有这道闸就会把无关原文包装成答案。
- **重评估触发**：前端接入后若发现 `degraded` 字段无人消费，说明契约设计有问题，应重新约定而不是删字段。

### D9 · bge-m3 作为本地 embedding（1024 维）

> 状态变更 2026-11-05：原列于「二、已定待验证」，E4 跑完后移入本档。原条目中的「E4 跑完前不改默认值」待办已解除，保留说明见下文。

- **决策**：替换当前的 DashScope `text-embedding-v4`（512 维）与 local-hash 兜底，走 Ollama / vLLM 的 OpenAI 兼容端点。
- **依据（选型）**：中文检索强（C-MTEB 约 71.4）、568M 参数、1024 维、8192 context、MIT、约 3~6GB 显存可跑（`docs/实验记录.md` §3.3，B 级多源）。
- **依据（E4 实测，2026-11-05）**：`docs/实验记录.md` §1.5，本机 RTX 3060 Laptop 6GB + Ollama 0.40.14，288 块、20 题：
  - 纯向量：bge-m3 Hit@1 14/20、Hit@5 20/20、MRR 0.825；local-hash（同 1024 维）2/20、7/20、0.212。
  - 编码成本：288 块冷启 18.7 s、热态 6.5 s，6GB 显存可稳定运行。
  - 题集并不偏字面：纯字面 17/20 已经很高，bge-m3 仍把 Hit@1 从 11/20 拉到 14/20、MRR 从 0.687 拉到 0.825，说明提升来自语义匹配而非关键词重合。
- **原重评估触发未命中**：原写「E4 显示 Hit@5 比 local-hash 高不到 2 题则先怀疑题集」。实测 +13 题，不触发。
- **备选**：bge-large-zh-v1.5、Conan-Embedding-v1、继续用云端 DashScope。
- **新重评估触发**：
  - 目标部署机没有 GPU，CPU 推理的 P95 不可接受 → 退回云端 DashScope（此时权重回到 D3 的 local-hash/云端口径，需重跑 E4）。
  - 题集扩到 100 题以上后，bge-m3 相对 DashScope v4 的优势消失。E4 没直接对比云端，这是缺口。
  - 生产并发下显存或吞吐不够（6GB 单卡同时跑 3B 生成模型时需重新估算）。
- **未落地**：`application.properties` 默认仍是 `hazmat.ai.enabled=false`（即 local-hash），启用云端时是 DashScope `text-embedding-v4`（512 维）。权重已按模型自动分档（见 D3），所以切 bge-m3 为默认时只需改 base-url/model/dimensions，并重跑全量评测刷新文档里的数字；不再需要手工改权重。

### D10 · 阶段 2 用 pgvector 存向量，正文留 MySQL

- **决策**：向量与过滤字段（`cas_no`、`doc_type`、`index_version`）进 pgvector，块正文仍在 MySQL；检索时先取候选 ID 再回表。
- **实现状态（2026-11-06，B3 已落地）**：`PgVectorStore` + 条件装配（`hazmat.vector.store=pgvector`），
  只建第二个 `DataSource`/`JdbcTemplate`、不建第二个 JPA EMF；检索 SQL 下推余弦与 `cas_no` /
  `doc_type` / `index_version` 过滤，HNSW `m=16, ef_construction=64`；维度按配置校验（bge-m3 1024 维），
  本地哈希 512 维向量会被明确拒绝而不是写进不同空间。**默认仍是 memory**——288 块时内存暴力更简单，
  pgvector 的价值在持久化、多实例与 10 万级余量，不是为了当前延迟。
- **依据**：持久化、多实例、标准 SQL 运维、为 10 万级留余量（`docs/实验记录.md` §3.1）。**不是因为当前 288 块慢**——这一点必须说清楚，否则会被「288 块为什么要上向量库」反问。
- **备选**：继续内存暴力、Milvus、Qdrant。
- **重评估触发**：E5 显示 10 万块时 HNSW 召回低于 95%，或过滤条件下的检索退化明显；或阶段 2 后数据量仍停留在几千块，pgvector 的运维成本大于收益。
- **E5/E6 反馈（2026-11-06，已触发召回条件）**：合成向量上 10 万块 HNSW 在 `ef_search=40`
  只有 Recall@10 0.530，拉到 400 才 0.815，`m=32` + `ef=200` 也只有 0.736；延迟不是问题
  （3~5 ms）。这条**没有推翻 pgvector 存储**，但说明「默认参数直接上 ANN」不成立：
  阶段 2 必须先用真实 bge-m3 向量重跑 E5，再定 `m`/`ef_search`；若真实向量仍达不到 0.95，
  备选是 `halfvec` 量化、降维模型或 IVFFlat，而不是硬堆 `m`。索引体积约 8 KB/块
  （10 万块 781 MB），也计入容量规划。数据见 `docs/实验记录.md` §1.7。

### D11 · `index_version` 在块上，`active_version` 在全局元数据，原子切换

- **决策**：重建写新版本、不删旧版本；切换时只改全局指针；旧版本保留一个重建周期后再清理。
- **实现状态（2026-11-06，B4 已落地）**：`msds_chunk.index_version`（B2 加列）标记块属于哪一版，
  `msds_index_meta` 增加 `active_version` / `previous_version` / `building_version` / `switched_at`，
  新增 `msds_index_version` 台账记录每版的 `ACTIVE` / `PREVIOUS` / `RETIRED` 状态。
  重建在锁内事务里写入全新版本的块（`textHash` 相同且四元组一致时复制向量与 `indexed_at`），
  提交后切指针并清理早于 previous 的版本；`POST /api/msds/rollback` 只交换 active/previous 指针。
  所有读取路径（字面索引构建、待编码块、状态、对账）统一走 `activeChunks()`，不再有「读全部块」的入口。
- **验证（E8，2026-11-06）**：本机 H2、302 块、3 次连续重建，每次 228~351 ms；4 个查询线程并发
  共 6098 次检索，异常 0、空结果 0，观察到 3 个不同 active 版本；回滚后检索仍可读。
  数字见 `docs/实验记录.md` §1.8。
- **边界**：只能回滚一版（更早的版本在重建时清理）；重建窗口内新块向量待编码，这段时间新内容
  只能靠字面路召回。E8 是 H2 单机小规模，不代表 MySQL 或 10 万块。
- **依据**：重建期间检索必须可用，且不能读到「删了一半」的索引。D7 解决的是单实例内存索引，这一条解决的是持久化与多实例。
- **备选**：原地覆盖、双表切换。
- **重评估触发**：E8 实测重建期间错误率不为 0，或旧版本占用的存储不可接受。

### D12 · 生成以抽取式为主，`/ask` 才调本地 3B

- **决策**：默认只返回原文片段 + 出处；只有显式问答接口才调用 Qwen2.5-3B，且引用校验失败时降级为抽取式。
- **依据**：安全场景零幻觉优先；「答错会出安全事故」。3B 模型在中文安全文本上的生成质量未验证，不能作为默认路径。
- **实现状态（2026-11-06）**：接口、生成客户端、引用校验与抽取式降级已落地。模型只看到前 5 条片段，回答里的 `[n]` 只能落在该范围内；越界或没有有效引用整段作废。抽取式按意图章节优先选句（误食→§4 等），无任何词面对应时拒答。`chat-enabled` 与 embedding 的 `enabled` 分开，默认都不开。
- **E9 结果（2026-11-06）**：本机 bge-m3 检索 + 在线 DeepSeek 生成。20 道可答题三轮里「生成」为 18~20/20、「引用命中标准节」19~20/20（同配置有波动）；4 道陷阱中 2 道明确拒答、2 道给出有原文依据的否定；另加 24 道库外问题（无关话题 / 库外试剂 / 库内试剂但 MSDS 不载的信息），修正拒答判定后 24/24 明确拒答；20 条完整回答逐条对照块原文，未发现与原文冲突的陈述。结构防线与拒答行为在真实模型上成立。
- **E9 之后补的配置**：生成端点可以独立于 embedding（`chat-base-url` / `chat-api-key`）。原因是本轮实测组合就是「本机算向量 + 在线做生成」，而 DeepSeek 没有 embeddings 接口；若强制共用 base-url，288 块编码会直接失败。默认仍回落到共用配置，同家服务不用多配。
- **本地 3B 对照（同日）**：默认的 `qwen2.5:3b` 在同题集上可答 13/20、引用命中标准节 10/20，库外拒答 22/24，还会把无关问题硬答。**这直接支持「生成默认关闭」**：当前默认模型不可用，换成在线模型又涉及数据出境，所以 `chat-enabled=false` 不变。
- **仍未验证**：忠实度只做了单人抽检（20 条、未查遗漏、非独立评审），不等于「内容正确率 100%」；库外拒答率只对这 24 道题成立；更大本地模型（7B/14B）未测。这三条在引用数字时必须一起说。
- **备选**：全部走生成、云端大模型生成。
- **重评估触发**：人工抽检证明生成回答的内容忠实度明显优于纯片段，且本地 3B 在 E9 类题集上不出现明显误拒，才考虑把生成改成默认路径。

### D13 · LangChain4j 只用于文档链路

- **决策**：设备手册与国标的 PDF/HTML 解析、切分、向量化可以用 LangChain4j；检索编排不用。
- **依据**：与 D2 同源。新数据源的解析是框架真正省事的地方，检索是项目深度所在。
- **备选**：全部自研解析、全部交给框架。
- **重评估触发**：阶段 2.5 的四档对比结论，或框架的 splitter 在真实文档上明显劣于自定义规则。

### D14 · 禁忌混放检测用结构化关系表，不用 RAG / 图数据库

- **决策**：把禁忌关系落成二元表（`chemical_incompatibility`），只比对台账里**当前有实物库存**的试剂，并按批次 `location` 判断是否真的同柜；RAG 只负责附上依据原文与条款号。
- **依据**：「甲醇的禁忌物有哪些」是穷举问题，top-k 检索一定会漏；关系是确定性的二元判定。GraphRAG 的成本与失败模式见 `docs/实验记录.md` §3.2、§3.4。
- **备选**：向量检索禁忌描述、Neo4j 路径查询。
- **重评估触发**：禁忌判定需要多跳（A 与 B 反应生成 C，C 与 D 冲突）时，图模型才有价值。
- **已落地（2026-11-05）**：
  - `V6__chemical_incompatibility.sql`：`(cas_a, cas_b)` 唯一、`CHECK (cas_a < cas_b)`，用 CAS 而不是 chemical.id 关联；表只存「有依据的禁忌」，不存「确认可混放」。
  - `IncompatibilityService` 一次读入规则建哈希表，与在库试剂两两比对；`GET /api/incompatibilities` 与 `GET /api/chemicals/{id}/incompatibilities` 只要求登录。
  - **柜位感知（同日补）**：规则命中只说明「禁配」，是否「混放」还要看物理位置。服务按化学 id 聚合所有 `availableQuantity > 0` 批次的 `location`，两种试剂的柜位集合有交集才进 `conflicts`；规则命中但分柜的进 `separatedConflicts`，只提示保持分离。每条记录带 `sharedLocations`，报告另给 `coStoredPairCount`、`coStoredUncoveredCount`。没有这一步时，18 种种子试剂分散在 13 个柜位，51 条规则命中会被全部误报成同柜违规。
  - 返回把 `conflicts` 与 `uncovered` 分成两个字段：**未覆盖只表示规则表没记录，不代表安全**。`IncompatibilityTest` 用「硫酸 + 过氧化氢」锁住这一点——这一对确实危险（接触可生成强氧化性/易爆体系），但当前 MSDS §10 没有直接禁配表述，所以必须留在未覆盖里等人工补资料。
  - 种子 `seed/incompatibilities.json` 共 51 对，依据全部来自仓库内 18 份 MSDS 第 10 节，`source` 写到具体 CAS 的章节，不编造 GB 15603 条款号；`IncompatibilitySeedDataTest` 校验 CAS 拼写、重复对与出处字段。演示数据在 `易制爆专柜 C-1` 刻意多放了一个过氧化氢批次，与高锰酸钾同柜，用于展示真实违规；生产应关闭演示种子。
  - **依据结构化（2026-11-06，B5-1）**：`V10__incompatibility_basis.sql` 给规则表加
    `source_type`（MSDS/GB）、`source_doc`、`source_clause`、`source_excerpt`、
    `verification_status`（VERIFIED/PENDING）。接口每条规则返回 `basis`，报告给出
    `basisCoverage{total,verified,pending,missing,verifiedRatio}`。三态的含义写死：
    `verified` 是「引文与文档对得上」，`pending` 是「有规则但依据未核」，`missing` 是
    「连来源都没填」；**未覆盖（uncovered）不属于这三态**，它是「规则表里根本没有这一对」，
    仍然单独返回。51 对全部回填 MSDS §10 的原文摘录，标 `VERIFIED`；GB 15603 没拿到
    授权全文，一条条款号都不造，宁可留 `PENDING`。
  - **尚未完成**：还没有按 GB 15603 条款号建关系；当前 51 对只覆盖种子里的 18 种试剂，换一批试剂必须重新导入，不能把「检查通过」当成全库安全。柜位仍是自由文本，没有主数据与拼写校验；不区分柜内层板，同一房间不同柜也不算同柜。`VERIFIED` 不是第三方合规复核，摘录也可能漏掉同节的其它禁配表述，核对要回原文。

### D15 · 撤销用 `token_version` 比对，不用 token 黑名单

- **决策**：`app_user.token_version` 存版本号，签发时写进 `tv` claim；停用、改角色、改密、logout-all 都自增；
  每请求比对 token 与库里的版本，不一致即 401。库查询带 30 秒本地缓存，管理接口改完主动清缓存。
- **依据**：黑名单要按 token 存一条记录并设 TTL，条目数随登录量增长，还得处理「黑名单比 token 活得更久」的清理问题；
  版本号是每用户一个整数，存量恒定，且天然支持「一键全部下线」。代价是每个登录用户首次校验多一次索引查询（之后走缓存），
  以及**多实例下最迟 30 秒生效**——单实例由接口主动 evict，是即时的。
- **实现（2026-11-06）**：`V8__user_token_version.sql`、`JwtService` 写 `tv`、`TokenVersionFilter`
  （挂在 `BearerTokenAuthenticationFilter` 之后，否则解码还没发生）、`TokenVersionService` 缓存、
  `AuthController` 的 `/password` 与 `/logout-all`、`UserAdminService` 的启停/改角色/重置密码。
  「最后一个启用中的 ADMIN」不能被停用或降级，否则没人能再进管理接口。
- **备选**：Redis 黑名单（需引入共享存储）、短 token + refresh token（需要前端配合刷新）。
- **重评估触发**：出现「必须秒级全网生效」的合规要求，或 token 校验的库查询成为瓶颈（届时先看缓存命中率）。

### D16 · 双存储不做分布式事务，MySQL 为事实源、pg 为可重建派生数据

- **决策**：编码成功先 `saveAll` 到 MySQL，再 `upsert` pg；pg 写失败只记指标与日志，**不回滚、
  不把整批判成编码失败**。缺口由 `POST /api/msds/reconcile` 按 MySQL 的「已编码」集合补写，
  `/api/msds/status` 的 `vectorRows` / `missingRows` 暴露差异。pg 不可用时向量路降级到字面检索。
- **依据**：两个库没有分布式事务；为了让 pg 与 MySQL 强一致而引入 2PC/XA，代价远大于收益，
  而向量本来就是可重建的派生数据——正文与编码状态才是事实。把 pg 失败算成 AI 编码失败会把
  故障范围从「向量路降级」放大到「整批重试、失败计数累加、编码队列提前暂停」。
- **取舍**：pg 侧允许短暂落后于 MySQL；写成功但未对账的窗口内，新块只能靠字面路检索。
  这不是「最终一致」的证明——没有后台定时对账，只有手动触发与状态计数。
- **备选**：2PC/XA、把向量与正文都放 pg、写 MySQL 前先写 pg（会留下「向量库有、台账没有」的幻影行）。
- **重评估触发**：检索对「新块可立即语义召回」有硬要求，或对账缺口在真实流量下持续非零
  （说明手动对账不够，需要定时任务与告警）。

### D17 · 业务单号用「日期 + 进程内自增序号」，冲突翻译成业务错误

- **决策**：`REQ` / `ST` 单号 = 前缀 + `yyyyMMdd` + 8 位十六进制序号（`common/DocumentNoGenerator`）。
  序号是进程内 `AtomicLong`，启动时随机播种；唯一索引仍是最后防线，插入时的
  `DataIntegrityViolationException` 翻译成 `BusinessException`（400，可重提），不落到 500。
- **依据**：单号只用于人眼识别与口头沟通，不要求连续。最初的「4 位随机数」在写路径压测里
  暴露了代价：734 次并发建单撞了 72 次唯一索引（10⁴ 空间，生日悖论），每次都是一个 500。
  「查当天最大号 + 1」则要多一次查询并引入串行点。进程内自增两者都不要，单 JVM 内
  2³² 次内确定唯一。
- **取舍**：多实例各自从随机位置自增，仍可能撞号（每天 1 万单约 1%），所以不能只靠生成器，
  必须同时处理唯一约束冲突。代价是调用方要能识别这条业务错误并重提。
- **备选**：数据库序列（MySQL 无原生序列，要建号段表并加行锁）、号段服务、UUID/雪花 ID
  （丧失可读性，且时间前缀已经承担了分天归档的作用）。
- **重评估触发**：部署到多实例且撞号重提在监控里持续出现，或单号被外部系统要求连续。
