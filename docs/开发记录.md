## 一、问题排查

### 1. 种子数据使用绝对日期，到期后应用启动失败（2026-10-10）

- **现象**：应用启动时种子灌到第三个批次抛 `BusinessException`，整个应用起不来。
- **原因**：演示需要“已过期”和“临期”两类批次，种子文件里写的是绝对日期；而入库校验不允许已过期批次。这两条在写入时就是矛盾的，只因当时日期还在未来没有触发。
- **解决**：种子 JSON 改为相对天数（`inboundDaysAgo` / `expireInDays`），并走带入库日期的 `StockService.inbound` 重载，让过期校验相对“入库那一天”计算。
- **验证**：应用正常启动；`RequisitionFlowTest#cannotInboundExpiredBatch` 覆盖入库拒绝过期批次。
- **取舍**：种子文件不再是可直接阅读的绝对日期，但数据不会随时间腐烂。
- **来源**：`seed/SeedRunner` 类注释。

### 2. JDK 版本过高导致 Lombok 静默失效

- **现象**：编译出现大量“找不到符号”，全部指向 Lombok 生成的 getter/setter，看起来像代码损坏。
- **原因**：PATH 中的默认 JDK（如 JDK 26）与当前 Lombok 不兼容，注解处理器没有生效，但构建没有直接报 Lombok 错误。
- **解决**：固定用 JDK 21 构建，`start.sh` 中显式设置 `JAVA_HOME`。
- **验证**：`java -version` 确认为 21 后重新构建通过。
- **来源**：`hazmat-ledger/README.md`「环境要求」。

### 3. 乐观锁冲突不能在原事务内重试

- **现象**：两位审批人几乎同时点“通过”，后写的一方被 `@Version` 拦下。若直接把冲突报给用户，流程会丢掉合法的第二票。
- **原因**：同一事务里抛过 `OptimisticLockingFailureException` 之后，持久化上下文已经不可用，不能就地重试。
- **解决**：`RequisitionService.review` 用 `TransactionTemplate` 控制事务，冲突时换新事务重读重判，最多 3 次。
- **验证**：`DualReviewTest` 的并发场景断言两票都算数。
- **取舍**：审批事务边界从注解改为显式模板，代码稍复杂，但冲突语义正确。
- **来源**：`service/RequisitionService` 类注释与 `review` 方法注释。

### 4. 并发与乐观锁测试加 `@Transactional` 会假绿

- **现象**：给测试类加上 `@Transactional` 后，并发断言仍然通过，但没有真正验证并发。
- **原因**：并发测试需要多个事务真正同时打同一行；乐观锁测试需要实体在事务外是游离态，否则版本比对不会触发。
- **解决**：`StockConcurrencyTest`、`DualReviewTest`、`RequisitionFlowTest` 刻意不标 `@Transactional`。
- **验证**：去掉注解后，并发与版本冲突场景才真实执行。
- **来源**：三个测试类的类注释。

### 5. H2 默认锁等待时间太短，并发测试随机失败

- **现象**：30 个线程争同一行时，测试偶尔失败，看起来像扣减逻辑有问题。
- **原因**：H2 默认 `LOCK_TIMEOUT` 只有 1～2 秒，“排队等锁”被误判成失败。
- **解决**：连接串设置 `LOCK_TIMEOUT=10000`。
- **验证**：`StockConcurrencyTest` 稳定通过。
- **来源**：`src/main/resources/application.properties` 注释。

### 6. `save` 不 `flush`，方法内接不住乐观锁异常

- **现象**：`try/catch` 包住了保存逻辑，但乐观锁异常仍然从上层冒出来，没有翻译成业务提示。
- **原因**：`save` 只是把实体挂进持久化上下文，真正的 UPDATE 在事务提交时才发出，那时已经离开方法。
- **解决**：需要就地拦截异常的地方改用 `saveAndFlush`。
- **验证**：`RequisitionFlowTest` 的乐观锁与状态机断言。
- **来源**：`RequisitionService#saveWithOptimisticCheck` 注释。

### 7. IDE 报 Lombok 初始化失败，Maven 构建正常（2026-10-26）

- **现象**：编辑器中打开 `ChemicalController` 时，IDE diagnostics 报 `NoClassDefFoundError: Could not initialize class lombok.javac.Javac`。
- **原因**：IDE 当前使用的 JDK 与项目要求的 JDK 21 不一致，Lombok 注解处理器加载失败。和历史上“JDK 26 编译出现大量找不到符号”是同一根因的不同表现。
- **解决**：以 JDK 21 的 Maven 构建结果为准；IDE 的 project SDK 需要切到 JDK 21。
- **验证**：`./mvnw test -Dtest=ScrapTest` 用 Java 21.0.11 编译并通过 5 个测试。

### 8. 别的试剂正文提到甲醇，把甲醇的答案挤下去了（2026-10-26）

- **现象**：`q=甲醇 闪点` 的 top1 是高锰酸钾 §9，不是甲醇 §9。高锰酸钾的理化特性里写着「溶于丙酮、甲醇」。
- **原因**：两处叠加。一是查询侧把「甲醇」拆成单字「甲」「醇」，单字命中所有提到这两个字的块，而高锰酸钾那块正文里确实有「甲醇」二字；二是索引侧对单字也计分，高频字靠数量堆出了分数。
- **解决**：查询侧只保留长度 ≥ 2 的 token，整句都是单字时才退回单字；名称 token 在块内的词频强制截断为 1。
- **验证**：`MsdsSearchTest#flashPointQuestionHitsPhysicalPropertiesSection` 从失败转为通过，top1 为甲醇 §9。
- **取舍**：查单个字（如「酸」）时噪声仍然大，这是字面路的固有边界，不靠堆规则解决，留给向量路。
- **来源**：`MsdsLiteralIndex#queryTokens`、`#build` 的注释。

### 9. 长度归一化的方向反了，最短的块被顶到第一（2026-10-26）

- **现象**：为压掉长块的优势，试过把得分除以 `√tokenCount`。结果 `q=硫酸 稀释` 的 top1 从 §2 变成 §13（废弃处置）——§13 正文最短。
- **原因**：归一化假设「长块得分天然更高，需要折价」，但字面得分是逐 token 累加的，长块只有在真的重复命中时才更高。除以长度等于系统性奖励短块，与「有没有回答问题」无关。
- **解决**：放弃长度归一化，改为 TF 对数加权（`1 + ln tf`），抑制重复而不改变不同块之间的相对关系。
- **验证**：`MsdsSearchTest#dilutionQuestionFindsHandlingSectionAmongTopHits` 改为断言 top5 含 §7，并注明字面路分不开 §2/§7/§13，精确排序交给向量路与 RRF。
- **取舍**：接受字面路排序不精确，不再为它堆人工规则。

### 10. 同一试剂在界面和索引里是两个名字（2026-10-26）

- **现象**：检索结果里显示「无水乙醇」，但索引用的是 MSDS 文件第 1 节解析出的「乙醇」。用户按界面名字搜，命中的是另一条线索。
- **原因**：`chemicalName` 有两个来源——`Chemical` 档案和 MSDS 文件正文，两处各取各的，没有约定谁优先。
- **解决**：`rebuild()` 优先用档案名，取不到才从第 1 节解析；点名加权比对前去掉「无水」「十水」前缀；块内容里的 `[化学品名]` 前缀统一用档案名，重建后 hash 自然更新。
- **验证**：重启后 `GET /api/msds/search` 返回的名称与 `GET /api/chemicals` 一致。
- **取舍**：档案名是唯一权威名称；文件内名称仅作兜底。若两个名字差异大到双字都不同（如别名），仍需靠同义词扩展补。

### 11. 「误食」在 MSDS 里写作「食入」，用户问法召回不到（2026-10-26）

- **现象**：`q=误食 甲醇` 的 top1 是无水硫酸钠 §4，因为那一节写了「大量误食会腹泻」；甲醇 §4 写的是「食入」，不含「误食」二字。
- **原因**：字面路按双字匹配，认不出「误食」与「食入」是同一件事；而库里恰有另一份文档字面命中了用户的原词。
- **解决**：加极简同义词扩展（误食/误服/吃下/吞下 → 食入，沾到 → 皮肤接触，溅到眼睛 → 眼睛接触，着火/起火 → 闪点、易燃），并对查询点名的试剂整体加权 ×3。
- **验证**：修复后 `q=误食 甲醇` top1 为甲醇 §4；`MsdsSearchTest#colloquialWordForSwallowingReachesFirstAidSection` 覆盖。
- **取舍**：不引入分词器与同义词库——没有题集时堆词表改坏了看不出来。当前 8 条只来自实测召回失败，阶段 3 要逐条对比加入前后的 Hit@5，没提升的删掉。
- **来源**：`MsdsQueryExpander` 类注释。

### 12. 不同测试配置共用一个 H2 命名库，后启动的上下文把表重建了（2026-10-26）

- **现象**：新增带独立 properties 的 `@SpringBootTest` 后，已有 MSDS 测试偶发查不到块，看起来像索引没建。
- **原因**：`jdbc:h2:mem:hazmatdb;DB_CLOSE_DELAY=-1` 是同一个 JVM 内共享的命名库。每个新上下文启动时都会执行 `ddl-auto=create-drop` 的 DROP/CREATE，把前面缓存上下文的数据清空；而前面那个上下文的 `ApplicationReadyEvent` 已经跑过，不会再补数据。
- **解决**：验证向量路径的测试类各自使用独立库名（`msds-vector-local`、`msds-vector-failure`）。只改 properties、不改库名的测试类之间仍有这个隐患，新增带配置覆盖的 `@SpringBootTest` 时要一并处理。
- **验证**：全量 47 条通过，且与测试类执行顺序无关。
- **来源**：两个 `MsdsVector*Test` 的 `@SpringBootTest(properties = ...)`。

### 13. 后台编码与测试断言并发，结果不稳定（2026-10-26）

- **现象**：`ApplicationReadyEvent` 会异步启动编码，测试里紧接着调 `rebuild` 或查 `status`，有时看到「编码中」的中间态，断言偶发失败。
- **原因**：编码在守护线程里跑，测试方法没有等待点；数据量小时大多数时候刚好跑完，看起来是随机红。
- **解决**：surefire 系统属性统一设置 `hazmat.ai.encode-on-startup=false`；需要验证编码的测试自己同步调用 `encodePending`。生产默认仍是启动即编码。
- **验证**：`MsdsVectorLocalTest`、`MsdsVectorFailureTest` 全部同步执行，多次运行结果一致。
- **来源**：`pom.xml` 的 surefire 配置。

### 14. curl 中文查询返回空数组，不是接口报错（2026-10-26）

- **现象**：`curl -G --data-urlencode "q=误食 甲醇"` 返回 `{"data":[]}`，第一反应是索引坏了。
- **原因**：Git Bash 下参数编码把中文变成了别的字节，服务端收到的查询词与索引对不上，正常返回空结果。接口本身没有问题。
- **解决**：用百分号编码（`q=%E8%AF%AF%E9%A3%9F%20%E7%94%B2%E9%86%87`）或 Postman/浏览器验证。
- **取舍**：这比之前记录的「中文导致 500」更隐蔽——500 至少知道出错了，空结果容易被误判成检索缺陷。终端验证中文字段时优先用百分号编码。

### 15. 锁在事务里层，并发重建仍然各插一份（2026-10-26）

- **现象**：审查时构造两个并发 `POST /api/msds/reindex`，块数从 288 变成 576。
- **原因**：`rebuild` 是「查旧块 → 删 stale → 插新块」的读改写。第一版把锁放在 `@Transactional` 方法体内，而事务的提交发生在 Spring 代理返回之后：方法体 `finally` 解锁时，第一个事务还没提交，第二个线程拿锁后读到的仍是旧快照，于是又插一遍。
- **解决**：去掉方法上的 `@Transactional`，改成 `rebuild()` 先拿 `ReentrantLock`，再用 `TransactionTemplate.execute(...)` 执行 `doRebuild()`。锁在外、事务在内，第二个线程拿锁时上一个事务已经提交。单实例有效；多实例部署要靠数据库唯一约束或分布式锁，当前项目没有多实例。
- **验证**：`MsdsSearchTest#concurrentRebuildDoesNotDuplicateChunks` 用 4 个线程同时重建，块数与内存索引条数都不变。
- **来源**：`MsdsIndexService#rebuild` 的类注释。

### 16. 无界编码队列 + 未鉴权的重建接口（2026-10-26）

- **现象**：`reindex` 每调用一次就向单线程 executor 提交一个任务。`Executors.newSingleThreadExecutor` 的队列没有上限，脚本循环调用可以把任务堆到 OOM；每次调用还会清掉「编码暂停」，反复触发模型调用。
- **原因**：接口按演示项目处理，没有用户体系也就没有鉴权；线程池选了最省事的工厂方法。
- **解决**：换成 `ThreadPoolExecutor(1, 1, ..., ArrayBlockingQueue(8), 拒绝时记日志)`。丢弃安全——排队中的任务会按最新库状态重新取待编码块，不会漏块。鉴权不在项目内自制：当前没有用户体系，加一个半吊子 token 只会制造「看起来安全」的错觉；文档明确要求部署时由网关或内网访问控制兜住。
- **验证**：`MsdsSearchTest` 并发重建正常；前端/脚本连续调用不再堆积任务（队列满会打印一条 warn）。
- **取舍**：没有加「两次 reindex 最小间隔」限流。它会破坏「修好 key 后立即重试」的语义，而真正的成本防线是鉴权，不是节流。

### 17. 查询长度没有上限（2026-10-26）

- **现象**：`GET /api/msds/search?q=` 接受任意长字符串。分词、同义词扩展、逐块打分都与查询长度线性相关，未认证接口可以被一条超长参数放大 CPU 与内存。
- **解决**：`MsdsSearchService` 限制 200 字符，超出抛业务异常（400）。
- **验证**：`MsdsSearchTest#overlongQueryIsRejected`。
- **来源**：`MsdsSearchService` 的 `MAX_QUERY_LENGTH`。

### 18. `NaN` 能通过 `Float.parseFloat`，并会污染排序（2026-10-26）

- **现象**：审查向量解码时发现两处静默问题。`Float.parseFloat("NaN")` 成功，`cosine` 得到 `NaN`；Java 的 `Double.compare` 把 `NaN` 视为最大，于是一条坏向量会稳定排在第一位。另外 `vector` 是文本列，若被写入超长内容，`split` 会先分配一个巨大的数组。
- **解决**：`VectorCodec.decode` 拒绝非有限值与超过 1 MB 的存量串，返回 `null`，上层按「这一块没有可用向量」处理，下一轮编码会重算。`VectorCodec` 只认自己写出的格式，不需要兼容第三方写入。
- **验证**：`VectorCodecTest#nonFiniteValuesAndOversizedStorageDecodeToNull`。
- **来源**：`VectorCodec.decode`。

### 19. 等权 RRF 融合反而低于字面基线（2026-10-26）

- **现象**：向量路接入后，按常见做法把两路权重设成 1:1，24 题题集上融合 Hit@5 只有 14/20，低于字面路单独的 17/20。融合不是「相加就好」，弱的那一路会把字面路本来排进前 5 的结果挤出窗口。
- **原因**：本轮向量路是本地哈希，本质仍是字面重合，且比倒排更粗（没有 IDF、没有名称加权），精度明显低于字面路。两路能力相近时等权才合理。
- **解决**：权重可配，默认改为字面 3 : 向量 1。按 2:1 → 17、3:1 → 18、4:1 → 18 实测，取 3:1；再高的权重等于退回纯字面，融合失去意义。
- **边界**：这个权重是本地哈希下的结论，接入云端 embedding 后必须重跑评测重标，不能当固定常数。
- **验证**：`MsdsRetrievalEvalTest` 打印三路 Hit@5 并断言融合不低于字面；具体数字见 `docs/msds-rag-设计.md` §8.2。
- **来源**：`MsdsRetrievalProperties`、`application.properties` 中 `hazmat.msds.retrieval.*` 的注释。

### 20. `spring-boot-starter-security` 不包含 resource server，JWT 相关类编译不过（2026-10-27）

- **现象**：接入 JWT 时只加了 `spring-boot-starter-security` 与 `spring-security-oauth2-jose`，`JwtAuthenticationConverter`、`oauth2ResourceServer` 均提示找不到。starter 提供的是 Web 安全的基础设施，不包含 Bearer token 资源服务器。
- **解决**：显式加 `org.springframework.security:spring-security-oauth2-resource-server`（jose 仍需要，`JwtEncoder/JwtDecoder` 在其中）。
- **附带**：`roles` claim 不是默认权限来源，必须自定义 `JwtAuthenticationConverter` 映射成 `ROLE_*`；否则 `hasRole('ADMIN')` 永远不成立，表象是 403，很容易误判成权限规则写错。
- **来源**：`pom.xml`、`SecurityConfig#jwtAuthenticationConverter`。

### 21. `@PreAuthorize` 的拒绝异常不走 Security 的 AccessDeniedHandler（2026-10-27）

- **现象**：方法级权限在 Controller 调用时抛 `AuthorizationDeniedException`（`AccessDeniedException` 子类）。它发生在 DispatcherServlet 内，先被 `@RestControllerAdvice` 接住；如果全局处理器没有对应条目，会被兜底的 `Exception` 分支转成 500，而不是 403。
- **解决**：`GlobalExceptionHandler` 同时处理 `ForbiddenException` 与 `AccessDeniedException`。filter 层的认证失败仍由 `RestAuthenticationEntryPoint` / `RestAccessDeniedHandler` 写 JSON——两条路径都得配。
- **验证**：`SecurityIntegrationTest` 对普通用户调用建档、审批、`/api/msds/status` 均断言 403 与 `code=403`。
- **来源**：`GlobalExceptionHandler#handleForbidden`。

### 22. 增量编译沿用 IDE 产出的坏 class，真实错误被 `Unresolved compilation problem` 掩盖（2026-10-27）

- **现象**：IDE 因 Lombok 与 JDK 版本不匹配报大量假错误，同时把带 `Unresolved compilation problem` 的 class 写进 `target/classes`。随后 `./mvnw test` 增量编译没有重编该文件，启动直接失败；`clean` 之后才暴露真实原因：`List<SimpleGrantedAuthority>` 不能赋给 `Collection<GrantedAuthority>`（泛型不变性），需要显式写成 `.<GrantedAuthority>map(...)`。
- **解决**：遇到 `Unresolved compilation problem` 先 `./mvnw clean test`，不要根据 IDE 的诊断改代码；判断编译是否真的通过以 Maven 为准。
- **来源**：`SecurityConfig#jwtAuthenticationConverter`。

### 23. 非法 JSON 请求体落到兜底分支，返回 500（2026-10-27）

- **现象**：手工验证时在 Git Bash 里用 curl 发送中文请求体，终端用 GBK 编码，服务端解析失败抛 `HttpMessageNotReadableException`，被全局异常处理的 `Exception` 兜底转成 500。调用方看到的是「服务器内部错误」，实际是自己发错了请求体。
- **解决**：显式处理 `HttpMessageNotReadableException`，返回 400 与「请求体不是合法的 JSON，或字段类型不匹配」。这和问题 14 是同一个编码现象的两端：终端编码导致发送失败，服务端应当把它归为调用方错误。
- **验证**：`SecurityIntegrationTest#malformedJsonReturns400`。
- **来源**：`GlobalExceptionHandler#handleUnreadableBody`。

### 24. 未匹配到接口的路径被兜底成 500（2026-10-27）

- **现象**：验证 actuator 只暴露 `health` / `info` 时，带 token 访问 `/actuator/env`，返回 500 而不是 404。拼错一个 URL 也会得到「服务器内部错误」。
- **原因**：Spring 6.1 起，未匹配到 Controller 与静态资源的请求抛 `NoResourceFoundException`，它继承自 `ServletException`，被 `GlobalExceptionHandler` 最后的 `Exception` 分支接住，翻译成 500。
- **解决**：显式处理 `NoResourceFoundException` 返回 404 与「接口不存在」。这类错误是调用方走错了路径，不是服务端故障，500 会误导排查方向。
- **验证**：`SecurityIntegrationTest#healthIsPublicButOtherActuatorEndpointsAreNot` 断言 `/actuator/env` 为 404。
- **来源**：`GlobalExceptionHandler#handleNoResource`。

### 25. BuildKit 缓存挂载遮蔽 `/root/.m2`，Maven 绕过了国内镜像（2026-10-27）

- **现象**：Dockerfile 里已经把 `docker/maven-settings.xml` 拷到 `/root/.m2/settings.xml`，但构建日志显示 Maven 仍然 `Downloading from central: https://repo.maven.apache.org/...`，每个依赖都要等几秒。
- **原因**：`RUN --mount=type=cache,target=/root/.m2` 会在这一步把缓存卷挂到 `/root/.m2`，**覆盖镜像里该路径已有的内容**，settings.xml 因此不可见。Maven 找不到用户级配置，回落到默认的 Maven Central。
- **解决**：settings.xml 改放到 `/build/maven-settings.xml`（与缓存挂载的目录无关），构建命令显式 `-s /build/maven-settings.xml`。
- **验证**：构建日志里出现 `Downloading from aliyun-public: https://maven.aliyun.com/...`，依赖下载明显加快。
- **取舍**：settings.xml 不能放在用户级默认位置，构建命令多一个参数；换来的是缓存与镜像配置可以同时生效。
- **来源**：`Dockerfile` 构建阶段注释。

### 26. properties 文件里的行尾注释被当成了密码的一部分（2026-10-27）

- **现象**：容器化部署时应用启动失败，Flyway 报 `Access denied for user 'root'@'172.22.0.3' (using password: YES)`。但在同一个 MySQL 容器里用 `mysql -uroot -p<同一个密码>` 从另一个容器连接是成功的，密码显然没错。
- **原因**：`application-mysql.properties` 里写的是
  `spring.datasource.password=${DB_PASSWORD:88888888}   # 默认值仅供本地开发`。
  `.properties` 格式只把行首（或前有空白）的 `#` 当注释，**行内 `#` 不是注释**；于是密码实际变成
  `root-demo-password   # 默认值仅供本地开发`，连同空格一起送给了 MySQL。
- **解决**：注释单独成行，密码行只留占位符。`compose.yaml` 同时改为用
  `SPRING_DATASOURCE_USERNAME/PASSWORD` 直接覆盖，不再经过 profile 里的占位符。
- **验证**：重建镜像后应用启动，Flyway 建表成功，登录与种子数据接口正常（见下文实测记录）。
- **取舍**：MySQL 的配置从此至少要真正连一次才能确认，不能再靠「H2 能跑」推断。
- **来源**：`application-mysql.properties` 密码行注释。

### 27. 分页测试里断言绝对 id，第二个测试方法就开始红（2026-10-27）

- **现象**：`sort=id,desc` 的测试断言 `content[0].id` 等于 4（本用例插入的 4 条试剂），第一个方法通过，之后的方法全部失败。
- **原因**：`@BeforeEach` 里的 `deleteAll` 只删数据，**不会重置 H2 的自增序列**。第二次执行时新插入的 id 从 5 开始，`4` 不再是最大值。这同样适用于 MySQL：`DELETE FROM` 不会回退 `AUTO_INCREMENT`。
- **解决**：不写死 id，改为从仓储里取当前最大 id 再比较；或者只断言「第一页与第二页的 id 集合无交集、合起来恰好等于总数」。
- **验证**：`PagingQueryTest#sortWhitelistIsEnforced`、`#stableSortAppendsId`。
- **来源**：`PagingQueryTest`。

### 28. 把 `balanceAfter` 当成试剂总余额，断言对不上（2026-10-27）

- **现象**：甲醇分三次入库到三个批次（10、20、30），按 `id desc` 取最新流水，断言 `balanceAfter` 为 60（试剂总量），实际返回 30。
- **原因**：`StockLedger.balanceAfter` 记的是**该笔流水所在批次的余额**，不是该试剂所有批次的合计。出库时也一样，读的是 `currentQuantity(batchId)`。合计另有 `sumAvailable` / `sumUsable`。
- **解决**：测试按语义断言 30，并在测试与 DTO 注释里写明「批次余额」。要展示试剂总量应另查库存视图，不要指望从流水里读出来。
- **验证**：`PagingQueryTest#ledgerIsPagedAndMissingChemicalReturns404`。
- **来源**：`StockService` 流水写入与 `LedgerResponse` 字段说明。

### 29. 「差异为 0 就不校验」让最常见的盘点路径完全不设防（2026-10-27）

- **现象**：手工实测盘点时发现，建单快照 2980，盘点期间报废 10（批次变 2970），
  实盘照样录 2980（差异 0），提交后**确认直接成功**。盘点单记的是「盘过 2980」，
  库里是 2970，而对账接口仍然返回 `consistent=true`（2970 = 2970）。
- **原因**：`StocktakeService.confirm` 最初的写法是「差异为 0 就 `continue`」，
  本意是不写 `quantity=0` 的噪音流水；但 `continue` 连 `adjustTo(book, actual)`
  的条件更新一起跳过了，零差异条目**完全不受账面基准保护**。
  而零差异恰恰是最常见的路径——多数批次本来就对得上，于是一个本该发现漂移的机制，
  在最常见的路径上什么都没验证。
- **解决**：所有条目一律先执行条件更新（`SET available = actual WHERE available = book`），
  返回 0 就整单失效；只有 `diff.signum() == 0` 时才跳过写流水。语义变成
  「每一条都验证基准没变，只有差异为 0 才不记账」。
- **验证**：`StocktakeTest#zeroDiffItemStillVerifiesBookQuantity`；真实 HTTP 复测
  `POST /confirm` 返回 400「批次 ME-2026-02 的账面量在盘点期间发生了变化（建单时 3000.000）」，
  库存保持 2990、状态留在 `SUBMITTED`。
- **教训**：跳过某个分支时，要问「这条分支上原来还有哪些副作用是必须的」。
  这里 `continue` 跳掉的不只是写流水，还有唯一的一次正确性校验。
- **来源**：`StocktakeService.confirm` 注释与 `StocktakeTest`。

### 30. 入库查重把整表批次读进内存，吞吐随批次数线性下降（2026-10-27）

- **现象**：压测时向同一试剂连续入库，吞吐一轮比一轮低：
  376.9 QPS（该试剂 10→1900 批次）→ 152.7（→6600）→ 114.3（→7900），
  p95 从 39.7 ms 涨到 100.4 ms。换成另一个只有 10 个批次的新试剂，立刻回到 344 QPS
  ——退化只与**单个试剂的批次数**有关，与全库已有十万批次无关。
- **原因**：`doInbound` 用 `findByChemicalIdOrderByExpireDateAsc(chemicalId).stream()
  .anyMatch(b -> b.getBatchNo().equals(...))` 做批次号查重，把该试剂的全部批次
  实例化成实体再逐条比对。这是 O(n)，而且 n 是「这瓶试剂的采购次数」，
  会随着使用年限一直涨。`chemical_batch` 上当时只有 `(chemical_id)` 索引，
  没有 `(chemical_id, batch_no)`，也没有唯一约束。
- **第二个问题**：即使不慢，「先查后插」之间也有窗口——两个并发请求可以都通过
  检查，插出两条同号批次。串行测试永远发现不了。
- **解决**：新增 `V5__batch_no_unique.sql` 建 `(chemical_id, batch_no)` 唯一索引；
  查重改成 `existsByChemicalIdAndBatchNo` 的索引点查；`save` 外面接住
  `DataIntegrityViolationException` 转成 `BusinessException`，让并发冲突返回 400
  而不是 500。
- **验证**：同一试剂连续三轮各写约 3 万条，吞吐 3025.7 / 3166.0 / 3172.7 QPS，
  p95 稳定在 3.6 ms，**不再随批次数变化**（该试剂批次从 10 涨到 9 万）。
  同试剂重复批次号返回 400「批次号已存在: F-1」，另一个试剂用同一个批次号仍然成功
  ——唯一性按试剂隔离。`StockConcurrencyTest#concurrentInboundWithSameBatchNoKeepsOnlyOne`
  用 10 个线程同时提交同一个批次号，断言恰好 1 条落库、9 条被拒。
- **教训**：查重写成「读出来再比对」在小数据量下完全看不出问题，
  而且是那种会随使用时间越来越慢的写法。有唯一索引的话，第一反应应该是让数据库做。
- **来源**：`StockService.doInbound`、`ChemicalBatchRepository#existsByChemicalIdAndBatchNo`、
  `db/migration/V5__batch_no_unique.sql`。

### 31. 并发许可拿不到时整次检索返回空结果，把「忙」当成了「没有」（2026-11-05）

- **现象**：代码审查发现 `MsdsSearchService.search` 在 `limiter.tryAcquire()` 失败时
  直接返回空命中列表。此时字面索引明明在内存里、完全可用，用户却看到「没有相关章节」。
- **为什么这是正确性问题而不只是体验问题**：检索在安全场景下被用来回答「误食怎么处理」。
  「服务忙，暂时只给字面结果」和「这份 MSDS 里没有相关内容」是两个完全不同的结论，
  返回空列表会让后者被当成事实。设计原则「检索永不空白」本来就要求降级而不是消失。
- **原因**：闸门最初按「保护整个检索」设计，把字面路也一起圈了进去；
  但字面路是纯内存倒排扫描，真正的昂贵操作只有向量路的 embedding 调用与余弦扫描。
- **解决**：许可只闸向量路。拿不到许可时跳过向量检索，把空向量结果交给融合，
  `degraded=true`、`degradedReason` 写「检索并发已满，向量路降级，仅返回字面结果」。
  `SearchConcurrencyLimiter` 的类注释同步改成「向量路闸门」，说明为什么不用
  Hikari/Tomcat 线程池兜底、为什么用 `Semaphore`。
- **验证**：`ResilienceTest#searchDegradesToLiteralWhenPermitsExhausted` 占满许可后
  查询「甲醇 误食」，断言 `degradedReason` 同时含「并发已满」与「字面」、
  `hits` 非空且 `sources` 全是 `literal`。
- **来源**：`MsdsSearchService`、`SearchConcurrencyLimiter`、`ResilienceTest`。

### 32. 字面索引在事务提交前替换，回滚后内存指向不存在的行（2026-11-05）

- **现象**：代码审查发现 `MsdsIndexService.rebuild()` 在 `transactionTemplate.execute(...)`
  的回调内部就执行了 `literalIndex = MsdsLiteralIndex.build(saved, namesByCas)`。
  构建用的是事务里的实体，但此时事务还没提交。
- **后果**：一旦提交阶段失败（约束冲突、连接中断、事务超时），数据库回滚，
  内存里却已经换成了「按未提交数据构建」的新索引，检索会命中库里不存在/已删除的块。
  这类不一致不会报错，只会让结果慢慢对不上——比直接抛异常更难查。
- **解决**：`rebuild()` 在 `execute` 返回之后调用 `refreshFromDatabase()`，
  由它从已提交的数据重建索引与名称表；`doRebuild()` 只负责落库。
  代价是一次全表查询（当时 288 行），换来「索引只可能比库旧，不可能指向幻影行」。
- **一个顺带修正**：加 `hasChunksFor(casNo)`（委托 `MsdsLiteralIndex#containsChemical`），
  让安全入口能区分「这份 MSDS 没索引过」和「这次没查到」，详见设计取舍 #23。
- **验证**：增量重建后检索结果不变；`ChemicalSafetyTest` 覆盖 available 两态；
  全量 145 条测试通过。
- **来源**：`MsdsIndexService#rebuild`、`MsdsLiteralIndex#containsChemical`。

### 33. Ollama 安装器在非管理员 shell 下静默安装挂起（2026-11-05）

- **现象**：为跑 E4，`start /wait OllamaSetup.exe /S` 与 `/VERYSILENT` 都长时间无返回；
  当前 shell 的 `IsInRole(Administrator)` 为 `False`，安装器需要 UAC 交互，静默参数并不能绕过。
- **解决**：不改系统环境，改用官方发布页的 Windows zip，解压到独立目录后直接运行
  `ollama.exe serve`（`OLLAMA_HOST=127.0.0.1:11434`），模型落在用户目录。
  与安装版功能一致，且不写入 Program Files、不注册服务。
- **注意**：从国内镜像站下载大文件时，部分代理忽略 `Range`、断点续传会失效；
  下载后应先用发布页提供的 SHA256 校验，再执行，不要直接运行来路不明的二进制。
- **验证**：`curl http://127.0.0.1:11434/v1/embeddings` 返回 1024 维向量，
  `HAZMAT_E4=true ./mvnw -Dtest=MsdsEmbeddingCompareTest test` 两个模型都跑通。

### 34. `@SpringBootTest` 默认关闭指标导出，`/actuator/prometheus` 在测试里是 404（2026-11-06）

- **现象**：pom 加了 `micrometer-registry-prometheus`、`management.endpoints.web.exposure.include`
  也写了 `prometheus`，启动日志却是「Exposing 2 endpoints」，`/actuator/prometheus` 404，
  而同一上下文的 `/actuator/health` 一切正常。
- **定位**：`-Ddebug=true` 的条件报告显示 `PrometheusMetricsExportAutoConfiguration` 未匹配，
  原因是 `management.defaults.metrics.export.enabled` 被认为是 false；但配置文件里根本没有这个键。
  打印 `PropertySources` 才看到有一个名为 `test` 的 `MapPropertySource`，内容是
  `{management.defaults.metrics.export.enabled=false, management.simple.metrics.export.enabled=true, management.tracing.enabled=false}`。
- **根因**：Spring Boot 的测试支持（`ObservabilityContextCustomizerFactory`）在测试里默认
  关掉真正的指标导出、只留在 JVM 内的 `SimpleMeterRegistry`，避免测试实例把指标推到远端。
  这不是配置错误，是测试上下文的默认行为。
- **解决**：验证导出端点的用例加 `@AutoConfigureObservability(metrics = true, tracing = false)`。
  只开 metrics，避免为一个端点测试引入链路追踪依赖。
- **教训**：看到「健康检查正常、只有某个 actuator 端点 404」时，先怀疑测试上下文的默认裁剪，
  不要反复改 `exposure.include`——那个键本来是对的。

## 二、设计取舍

### 1. 条件更新与乐观锁按“是否需要先读”分工

- 扣库存不需要先读，用 `UPDATE ... WHERE available >= ?`，判断与扣减在同一条 SQL。
- 状态变更必须先读出当前状态才能判断，用 `@Version`，并顺带保护审批人、审批意见等字段。
- **来源**：`ChemicalBatchRepository#deduct`、`entity/ChemicalBatch`、`entity/Requisition` 注释。

### 2. 扣库存冲突可以放弃，审批冲突不能放弃

- 扣库存冲突说明货被别的事务领走了，放弃是正确结果。
- 审批冲突说明对方的票可能正是流程缺的第二票，必须重读重判。
- **来源**：`RequisitionService` 类注释。

### 3. 双人复核用中间态，而不是计数

- 若留在 `PENDING` 另记次数，“还需几人”的规则会漏到 Service 的 if 里；同一个人点两次也会被计数放行。
- 中间态 `PENDING_SECOND` 同时挡住“只批一次就出库”，留痕表无需新增字段即可区分第一人和第二人。
- **来源**：`entity/RequisitionStatus` 的 `PENDING_SECOND` 注释。

### 4. 单号用日期 + 进程内自增序号（2026-11-06 修订，2026-11-09 被号段方案取代）

- 最初是「日期 + 4 位随机数」：避免“查当天最大号 + 1”这个额外并发点，唯一性交给唯一索引。
  但注释里写的「撞了重试」并没有实现——写路径压测下 734 次并发建单撞了 72 次，
  每次都变成 500（见本文§三 2026-11-06 写路径压测）。
- 现在改为 `DocumentNoGenerator`：日期 + 进程内 `AtomicLong` 的 8 位十六进制。单 JVM 内
  确定性唯一，不查库也不加锁；多实例仍可能撞，插入时把 `DataIntegrityViolationException`
  翻译成 400 业务错误，调用方可重提。
- **来源**：`common/DocumentNoGenerator`、`RequisitionService#submit`、`StocktakeService#create`；
  决策见 `docs/架构决策.md` D17。
- **2026-11-09 更新**：`DocumentNoGenerator` 已删除，改为 `document_no_segment` 表号段
  + `DocumentNoService` 进程内块缓存，冲突时丢弃本地段重试一次。决策见 D22，实测见
  §三 2026-11-09 冻结前补齐。

### 5. 金额与数量一律 `BigDecimal`

- 0.001 mL 是日常精度，`double` 无法精确表示 0.1，累加几十次后对不上账。
- **来源**：`hazmat-ledger/README.md`。

### 6. 种子数据走真实入库路径

- `SeedRunner` 调用 `StockService.inbound`，而不是直接插表；每次启动相当于跑一次入库冒烟测试。
- **来源**：`seed/SeedRunner` 类注释。

### 7. 报废复用条件更新，返回余额而不是实体（2026-10-26）

- 报废与出库都需要从批次扣量，没有新增扣减 SQL，直接复用 `ChemicalBatchRepository#deduct`：判断“够不够扣”与扣减在同一条语句里，并发报废、报废与出库同时发生时都不会扣成负数。
- 接口返回 `ScrapResult`，余额用 `currentQuantity` 标量查询。原因是批量 update 不会同步持久化上下文，`findById` 会命中旧实体，拿到扣减前的值且不报错。
- 批次归属在 Service 再校验一次，防止路径中的 `chemicalId` 与 `batchId` 拼错导致跨试剂扣减。
- **验证**：`ScrapTest` 并发场景 30 线程各报废 10、库存 100，恰好 10 次成功，余量归零，`SCRAP` 流水总量恰好 100。

### 8. 报废是直接扣减 + 留痕，暂不引入审批单（2026-10-26，2026-11-09 已补审批流）

- 当前实现记录报废量、原因、操作人，并写一条 `changeType=SCRAP` 的流水；过期批次因此有了处置出口，库存视图不再一直提示“未处理”。
- 没有独立报废单和审批流。若合规要求报废审批，应在 `scrap` 前增加单据状态机，审批通过后再执行扣减，而不是把审批逻辑塞进库存服务。
- **验证**：`ScrapTest` 的过期报废、超量拒绝、跨试剂拒绝、未过期破损报废四条功能测试。
- **2026-11-09 更新**：已按上面写的方向补成 `ScrapOrderService` + `/api/scraps`；
  管理员应急入口保留。审批时扣减失败的分支与 `refType/refId` 语义见 D19。

### 9. 没有 key 也编码本地哈希向量，而不是留空（2026-10-26）

- 向量字段留空的话，无 key 环境中索引永远建不起来，阶段 3 的向量路、RRF 融合与阈值标定都只能「等有 key 再测」，离线无法回归。
- 本地哈希零成本、结果稳定，可以作为向量路的基线；它抓字面重合而非语义，所以阈值必须单独标定，不能沿用云端模型的数。
- 状态接口用 `model` 字段如实显示 `local-hash`，避免把兜底当成语义模型。
- **来源**：`HashingEmbeddingClient` 类注释。

### 10. 失败次数与暂停状态持久化，不只放内存（2026-10-26）

- 只放内存的话，重启会把同一批失败块再打一轮模型调用；key 失效时每重启一次就多烧一轮额度，而且从状态接口看不出「上次已经停过」。
- 失败次数落在 `msds_chunk.encode_failures`，暂停时间与原因落在 `msds_index_meta.paused_at/paused_reason`。解除暂停只有一个入口：显式 `POST /api/msds/reindex`。
- **来源**：`MsdsIndexMeta` 类注释、`MsdsVectorService` 类注释。

### 11. 重建与编码并发接受最终一致，不互相等待（2026-10-26）

- 重建清空旧向量时，正在请求中的那一批编码仍可能写回旧模型向量。这些块的模型名与元数据中的四元组不符，`hasUsableVector` 会判为不可用，下一轮编码重算；检索不会拿它们算余弦。
- 反过来让 `reindex` 等编码结束也不行：云端 288 块要几十秒，管理接口会一直挂着，用户以为超时。
- 因此只在重建这一侧加锁（问题 15），编码一侧靠「模型名 + 维度」识别失效向量，两条路径各自解决自己的问题。
- **来源**：`MsdsVectorService#prepareForReindex`、`hasUsableVector`。

### 12. 本地哈希下接受「§4 让位 §11」，用 Hit@5 而不是单题 top1 衡量（2026-10-26）

- 「误食 甲醇」在本地哈希向量里，§11 毒理学（正文含「食入」）的余弦高于 §4 急救措施，融合后 top1 是 §11。字面路本来也把 §11 排在前面，这是两路共同的局限，不是融合引入的。
- 没有为单题写特例规则（例如「误食」强制 §4）：那会让题集变成规则清单，换个问法就失效。检索层只保证相关块进入候选，语境判断留给后续生成阶段。
- 测试因此只断言「top5 含 §4」，排序质量由评测的 Hit@5 衡量。接入云端模型后这一情形应自然改善，届时重新评估是否需要特例。
- **来源**：`MsdsFusionTest#fusedHitsCarryBothSourcesWhenBothPathsAgree` 注释。

### 13. 身份只从 token 取，Service 仍保留显式 actor 参数（2026-10-27）

- 申请人、审批人、操作人如果留在请求体里，「撤回只能本人」「双人复核必须两个人」都能靠改参数绕过；因此 DTO 删掉了 `applicant` / `reviewer`，出库/核销/撤回也不再接受 `operator` 查询参数。
- Service 方法仍接收 `applicant` / `reviewer` / `operator`，由 Controller 从 JWT 的 subject 传入。这样并发测试与后台任务可以脱离 HTTP 认证上下文调用，不需要在每个线程里手工塞 SecurityContext；代价是「必须由调用方传对身份」，这条约束由 Controller 与测试共同守住。
- **来源**：`RequisitionController` 类注释、`RequisitionService#submit` 注释。

### 14. 角色写进 token，不每次请求查库（2026-10-27）

- 每次请求查库鉴权会让 JWT 失去无状态的意义，也把数据库重新放进每个请求的关键路径。
- 代价是角色变更与停用不会即时生效：token 过期前仍按旧角色放行。默认有效期 8 小时，接受这个窗口；要即时撤销需要 token 黑名单或用户级 token 版本号，本项目不做。
- **来源**：`SecurityConfig` 类注释、`AppUser#enabled` 注释。

### 15. 分页用 OFFSET + id 兜底，排序走白名单（2026-10-27）

- **背景**：试剂列表原来全量返回，审批列表也是。数据量小的时候看不出问题，但接口契约一旦是「裸数组」，以后加分页就要改前端。
- **做法**：统一 `PageResponse`（`content/page/size/totalElements/totalPages/hasNext`）；`PageQuery` 统一处理页大小上限（100）、白名单排序、追加 `id` 稳定排序、LIKE 通配符转义。
- **为什么不直接返回 Spring Data 的 `Page`**：它会把 `Pageable`、`Sort`、`pageable` 一起序列化，前端被绑在框架实现上；字段命名沿用 `content/totalElements`，前端学习成本为零。
- **为什么追加 `id`**：`createdAt` 在批量写入时可能相同，只按它排序时数据库不保证相同值的相对顺序，翻页会出现重复与遗漏。加 `id` 是成本最低的唯一化手段。
- **为什么不一开始就做游标分页**：本项目的数据量级（一个实验室的试剂与申请）用 `LIMIT/OFFSET` 足够，实现简单、能直接跳页。深翻页的退化已写进 README 的已知缺口——等数据量真到了再换，不在没有需求时提前复杂化。
- **为什么关键词不做全文检索**：SQL `LIKE '%x%'` 用不上索引，中文也没有分词。真正的全文检索要上数据库全文索引或独立引擎，属于引入新组件，不是分页功能的一部分。
- **来源**：`common/PageQuery`、`common/PageResponse`、`ChemicalController`、`RequisitionController`。

### 16. 台账签名存用户名，不存用户外键（2026-10-27）

- 用户被停用或改名后，历史审批仍要能读出来是谁签的。用户名唯一且不随显示名变化，比自增 id 可读，比中文姓名稳定。
- 代价是用户表与业务表之间没有数据库级外键，账号被物理删除后签名只剩字符串；因此用户只停用、不删除。
- **来源**：`AppUser` 类注释。

### 17. MyBatis-Plus 只进只读报表层，不替换 JPA（2026-10-27）

- **背景**：需要两个聚合报表——按「分类 + 单位」汇总库存与效期分布、按「日期 + 变更类型」汇总出入库趋势。都是 `LEFT JOIN` + `GROUP BY` + `CASE WHEN`，属于 JPA 写起来最别扭的一类查询。
- **做法**：引入 `mybatis-plus-spring-boot3-starter`，只在 `report/` 包使用；SQL 放 XML；报表返回自己的 Row 对象，不映射实体；写路径、实体、乐观锁全部留在 JPA。
- **为什么不全量替换 JPA**：写路径的并发正确性（条件更新、`@Version`、双人复核的冲突重试）已经按 JPA 的语义设计与验证过。换 ORM 不是改写法，是把这些语义重测一遍，收益与风险不成比例。
- **为什么不用 JPA 原生查询**：原生查询会把 SQL 拆成字符串常量与投影接口两半，改一个列名要动两处；XML 里是完整一条，可单独执行、可直接贴进数据库客户端核对。这是选型的分界线——**查询以集合运算为主时用 SQL 映射器，以对象状态变更为主时用 ORM**。
- **代价**：两套 ORM 的心智负担；Flyway 的 `validate` 只覆盖 JPA 实体，报表 SQL 的列名与类型只能靠测试和真实库发现；两套分页风格并存（报表刻意不分页，见 README）。
- **版本约束**：starter 必须带 `boot3`（`mybatis-plus-spring-boot3-starter`）。boot2 版用 `javax.*`，在 Spring Boot 3 上会因找不到 `javax.servlet` 起不来。
- **来源**：`pom.xml` 依赖注释、`report/` 包、`resources/mapper/ReportMapper.xml`。

### 18. 过载兜底：每层资源有上限，拿不到就在有限时间内失败（2026-10-27）

- **背景**：单库部署、前面没有网关与限流。默认配置下没有任何一层会先失败——Tomcat 线程堆到 200、连接池默认等 30 秒、报表聚合占着连接跑到底。流量突增时（爬虫、脚本误刷、报表被反复点）表现出来的是整个服务不可用，而不只是某个接口变慢。
- **做法**：把这四件事分开处理，而不是笼统地"加限流"，
  1. **连接与线程各自有界，且线程数大于连接数**（Tomcat 100 / Hikari 10）。让请求停在连接池，那里有 3 秒超时和明确的 503；如果先让 Tomcat 拒绝，调用方拿到的是连接被重置，连原因都没有。
  2. **报表 SQL 用 `Statement` 超时，而不是应用层 `Future.get` 超时**。前者能让数据库真正取消查询、释放连接；后者只是调用方不再等，数据库那边照跑，连接照样被占着——等于把问题从"等待"变成"泄漏"。
  3. **检索单独设闸门**（Semaphore 4 + 等 200ms）。它是纯 CPU 的融合打分，吃满 CPU 会连带拖慢台账读写；在全局限流之前先按功能隔离，热点就不会外溢到主业务。
  4. **登录失败按用户名计数并短时锁定**。BCrypt 每次几十毫秒是防离线爆破的优点，在线爆破时变成放大器：几十个无凭证请求就能占满一个核。锁定期直接跳过密码校验，省的正是被攻击时最紧张的 CPU。
- **为什么是 503 不是 500**：资源紧张时重试可能成功，SQL 写错必须报警。混成 500 会让监控天天误报，调用方也不知道该不该退避。`ReportService` 只把 `SQLTimeoutException` / `QueryTimeoutException` / `SQLTransientConnectionException` 译成 503，其它异常原样抛出——把真 bug 吞成 503，等于让它永远没人修。
- **为什么登录计数不按 IP**：实验室出口通常是同一个 NAT，按 IP 会把整个实验室一起锁掉。代价是知道用户名的人可以故意锁它 1 分钟，内部系统接受这个代价。
- **为什么计数放内存**：项目刻意不引入 Redis（见 README 4.1）。放内存意味着多副本各算各的、重启清零，定位就是"防脚本误刷与低级爆破"，不是"抗分布式撞库"。
- **为什么 liveness 与 readiness 分开**：数据库挂了应该摘流量而不是重启进程，后者治不好数据库。`SecurityConfig` 里 health 必须写成 `/actuator/health/**`——只写精确路径会让子探针返回 401，容器拿到 401 会一直重启。
- **代价与边界**：容量参数是估的初值，没有压测依据；登录计数与检索许可不跨实例；报表超时在本地数据量下触发不了，只能靠 mock 验证翻译逻辑。

### 19. 盘点的账面量必须冻结，调账必须校验基准（2026-10-27）

- **问题**：入库、出库、报废都只在账内自洽，没有任何机制能发现**漏登记的动作**（移液没记、倾洒没报、拿错瓶子）。账会慢慢偏离实物，而库存视图读批次表、流水页读流水，各自都「正常」。盘点是把两条线对上的唯一动作，也是系统里唯一会修改历史余额的地方。
- **为什么按批次盘**：库存记在批次上，「这瓶甲醇还有多少」才是能数出来的。按试剂盘只能得到总数，总数对得上不代表批次对得上，差异也落不到哪一瓶。
- **为什么账面量连快照带冻结**：实盘量的语义是「相对于我数的那一刻」。不冻结的话，录入过程中别人出库一次，实盘减账面算出的差异就是错的。
- **为什么确认用条件更新而不是直接覆盖**：`UPDATE ... SET available = :actual WHERE id = :id AND available = :book`，返回 0 就说明盘点期间库存被改过，整张单失效。直接覆盖会把期间发生的业务量悄悄吞掉，而且对账还会显示「平」——错误被完美掩盖。
- **为什么整单原子、不允许部分成功**：剩下的条目会基于一个已经失效的快照，后续确认时必然再失败；而且「确认了 47 条、失败 3 条」这种中间态没人能解释清楚。
- **为什么差异写流水而不是改余额**：台账只增不改。盘亏 -20 与「这条记录被改成 2980」是两件事，前者可追溯，后者抹掉历史。写流水之后 `balanceAfter` 照常记，对账立刻能重新对平。
- **为什么零差异也要校验基准**：见「问题排查 #29」，这是实测踩出来的。
- **为什么对账分两层**：只看总量，两个批次一多一少互抵就查不出来；只看逐批次，发现不了汇总口径问题。总量用含过期批次的 `sumAvailable`，因为对账比的是账实一致，与效期无关。
- **为什么不强制提交人≠确认人**：单管理员部署（很多小型实验室只有一个库管）下强制会把流程卡死。留痕保证审计回答得出「谁数的、谁认的」；真要分离，得先有「多人具备 ADMIN」这个部署前提。
- **单号规则同申请单**：`ST + yyyyMMdd + 4 位随机`，唯一性靠唯一索引，不做「查当天最大值 +1」。
- **来源**：`StocktakeService`、`StocktakeStatus`、`ChemicalBatchRepository#adjustTo`、`dto/ReconcileView`。

### 20. 开封后的可用期物化成一列，而不是四个查询各算一遍（2026-10-27）

- **问题**：`chemical_batch.expire_date` 是供应商按「未开封」标注的包装有效期。甲醇吸湿、过氧化氢缓慢分解、乙醚久置生成过氧化物——开封后稳定性重新起算。只看包装有效期，一瓶开封三个月、早已不能用的甲醇会被当成「还有半年」继续发出去。
- **方案**：批次上新增 `usable_until`，入库时等于 `expire_date`，开封时取 `min(expire_date, 开封日 + chemical.post_open_days)`。出库 FEFO 过滤、库存视图的可用总量、效期预警、报表临期/过期统计**全部只读这一列**。
- **为什么不四处现算**：`min(expire_date, opened_at + post_open_days)` 本身只有一行，但判定点有四个（`findAvailableBatches`、`sumUsable`、`findExpiring`、`ReportMapper.stockSummary`），其中报表还是另一套 ORM 的 SQL。复制到第四处时必然有人漏掉一个 `is null` 分支，表现为「库存视图说可用、出库说不可用」，而这类不一致在台账系统里比直接报错更难查。
- **为什么只提前不延后**：取 `min`。开封不可能凭空延长保质期，否则「开一下封」就能让过期批次重新可发。
- **为什么重复开封直接拒绝**：覆盖 `opened_at` 会把可用期往回推，等于把一瓶一直开着的试剂重新赋予保质期，恰好抹掉正要跟踪的变质期。
- **为什么不写 `StockLedger`**：开封不改数量。塞一条 `quantity=0` 的流水会稀释「这一笔有变动」的信号，流水页也会出现与数量无关的大段行。开封是批次状态事件，记在 `opened_at/opened_by`，审计同样回答得出「谁在什么时候开的封」；对账接口也因此不受影响。
- **迁移约束**：`usable_until` 在脚本里允许 NULL，靠 `UPDATE chemical_batch SET usable_until = expire_date` 回填 + 实体 `@PrePersist` 兜底。不是偷懒——给已有列加 `NOT NULL` 的语法在 H2（`ALTER COLUMN ... SET NOT NULL`）与 MySQL 8（`MODIFY ... NOT NULL`）上不通用，而迁移脚本必须两边都能跑。允许 NULL 的真实风险是 `usable_until >= today` 对 NULL 恒为 unknown，会让历史批次从所有查询里消失，这才需要 `@PrePersist` 兜住一切绕过 Service 的写入。
- **已知边界**：开封不可撤销，误开只能报废或另开一批；`post_open_days` 事后修改不回溯已开封批次（可用期在开封那一刻落库，这是物化列的确定性，也是代价）；开封后没有独立的进度提醒，靠同一套 `withinDays` 预警，所以刚开封就可能立刻进入预警窗口。
- **来源**：`ChemicalBatch#usableUntil`、`StockService#openBatch`、`db/migration/V4__batch_opening.sql`、`BatchOpeningTest`。

### 21. 压测先定位瓶颈，再决定要不要缓存（2026-10-27）

- **问题**：项目一直的立场是「不用缓存」，但这只是判断，没有数字。
  在决定要不要给读路径加缓存之前，先用压测把瓶颈定位清楚。
- **方法**：H2 内存库装载两档数据（2000 试剂 / 2 万批次 / 22 万流水 / 5000 申请，
  与 1 万 / 10 万 / 110 万 / 2 万），固定并发、固定时长的 HTTP 压测，
  统计 QPS 与 p50/p90/p95/p99。
- **结论一：普通读不是瓶颈。** 分页列表、单试剂库存/流水/对账、申请列表
  在 32 并发下 3000~6000 QPS，p95 20 ms 以内；并发提到 64/100 时 QPS 不再上升
  （list 4099 → 4059 → 4248），延迟线性增长，说明已经到吞吐上限，而这个上限
  比真实需求高两个数量级。加缓存只能把这个上限推得更高，不解决任何实际问题。
- **结论二：只有两处随数据量线性退化。** 关键词搜索
  （`LIKE '%x%'`，5 倍数据 1845 → 521 QPS）与报表全表聚合
  （22 万流水 119.6 QPS → 110 万流水 22.4 QPS，p50 265 → 1515 ms）。
  前者命中行数随数据量涨，后者扫描行数随数据量涨，都是结构性问题。
- **为什么不给这两处加缓存**：报表的数据每次出入库都变，缓存要么 TTL 内读到旧账，
  要么写路径精确失效——而这正是项目刻意不引入的一致性复杂度。真要提升，
  方向是索引/预聚合（报表按日或按分类汇总）与全文索引（关键词换成 MySQL FULLTEXT
  或外部搜索引擎），不是把慢查询的结果存起来。关键词搜索的组合无穷，
  缓存命中率也撑不起这个代价。
- **来源**：`docs/开发记录.md`「2026-10-27 · 大规模压测」、`tools/bench/run-read.sh`、
  `bench/BenchDataLoader`。

### 22. 缓存按「陈旧有没有害」切边界，只放档案（2026-10-27）

- **问题**：压测证明读路径不缺缓存（见 #21），但「不需要靠缓存扛并发」不等于「缓存没有价值」。
  试剂档案在每个涉及库存的接口里都要被读一次——库存视图、流水页、对账、出库、盘点建单——
  它是典型的读多写少数据，每次读都打一次库属于纯浪费。
- **边界怎么切**：按「这份数据陈旧了会不会出错」分，而不是按「读得频不频繁」分。
  - `chemical` 档案：CAS 号、分子式、开封后可用天数——缓存半小时不会变错，**陈旧无害**。
  - `chemical_batch.available_quantity`、`stock_ledger`、报表聚合、盘点基准：**陈旧即错账**。
    缓存一旦引入，就要处理「Redis 扣了数据库没扣」这类问题；不引入就不会有。
- **为什么档案缓存永远不会脏**：`ChemicalController` 只有建档（`POST /api/chemicals`）与查询，
  **没有修改与删除入口**。档案只增不改，缓存不需要主动失效，一致性退化成「写入时放一份」。
  如果将来加了修改接口，这条推论就失效，必须改成写时删除缓存。
- **降级**：Redis 连不上时直接查库，接口不返回错误；写缓存失败只记日志，不影响已提交的写入。
  `spring.data.redis.timeout=1s` 限制单次白等时间；`management.health.redis.enabled=false`
  必须关——默认开启时 Redis 挂掉会让 `/actuator/health` 整体 DOWN，编排层会摘流量或重启，
  等于把一个可降级的依赖升级成不可用。缓存不是就绪条件。
- **做了与没做的**：空值哨兵（防穿透，1 分钟 TTL）、随机抖动（防雪崩，30m ± 5m）都做了；
  **击穿互斥没做**——回源是一次主键点查，为它加 SETNX 锁要多两次网络往返，收益不成比例。
  这是取舍，写在 `ChemicalCache` 类注释里，避免后来的人以为是遗漏。
- **测试**：`ChemicalCacheTest`（9 条，mock `StringRedisTemplate`，覆盖命中 / 未命中 / 哨兵 /
  不可用 / 坏 JSON / 开关关闭 / 写失败 / TTL）与 `ChemicalCacheFallbackTest`
  （3 条，把端口指向空端口，验证无 Redis 时档案查询、404、库存视图全部正常）。
  surefire 默认关闭缓存开关，避免整个测试套件因为本机有没有 Redis 而红绿不同。
- **来源**：`cache/ChemicalCache`、`cache/ChemicalCacheProperties`、`ChemicalService#findById`、
  README 4.1。

### 23. 安全入口用 `available` 区分「没有资料」与「这次没查到」（2026-11-05）

- **问题**：`GET /api/chemicals/{id}/safety` 天然有两种空结果：该试剂在库里
  根本没有 MSDS 块，或者有块但这次查询没匹配上。都返回 `hits=[]` 的话，
  前端只能对用户说「没查到」，用户无从判断是「换个问法再试」还是「去找管理员补资料」。
- **取舍**：返回体加 `available` 字段。`false` 表示索引里没有该 CAS 的块，
  同时给固定文案「该试剂尚未索引 MSDS 原文，暂无法提供安全信息」；
  `true` 且命中为空时给另一句「已索引该试剂的 MSDS，但本次查询没有匹配到相关章节」。
- **为什么不只靠 `message`**：文案是给人看的，分支判断要交给字段；
  前端不应该靠解析中文来决定显示「补资料」还是「换问法」。
- **为什么先查 `available` 再检索**：不先判断的话，配置了云端 embedding 时
  会为一个注定空的结果白花一次 API 调用；而且「没有资料」在业务上根本不该走检索。
- **边界**：`available` 只判断「有没有块」，不代表内容完整或足够新；
  它不替代 `needsRebuild`——后者表示索引配置与当前代码不一致，是另一个维度。
- **来源**：`ChemicalSafetyView`、`ChemicalSafetyService#safety`、`ChemicalSafetyTest`。

### 24. 检索依赖收在窄服务里，不让档案服务背上检索的故障面（2026-11-05）

- **问题**：安全入口需要「按 id 查档案 → 取 CAS → 检索」。最省事的写法是把
  `MsdsSearchService` 注进 `ChemicalService`，但那样所有查档案的接口
  （列表、库存、流水、对账）都会连带依赖检索模块的构造与配置。
- **取舍**：新增 `ChemicalSafetyService`，只做这一条链路，依赖
  `ChemicalService` + `MsdsSearchService` + `MsdsIndexService`；
  `ChemicalService` 保持只依赖档案仓储与缓存。
- **收益**：台账主线的单元/集成测试不需要感知检索模块；检索侧改坏、
  暂时不可用时，档案读写不受影响。故障面按服务边界隔离，而不是按包隔离。
- **不标 `@Transactional`**：档案读取走缓存、检索是内存扫描加一次可能的 embedding 调用，
  没有需要跨语句一致性的写操作；加事务只会多占一个连接。
- **来源**：`ChemicalSafetyService`、`ChemicalController`、设计文档 §5.1。

### 25. 融合权重按模型分两档，不写死一个比例（2026-11-05）

- **问题**：3:1 是在「无 key + 本地哈希」下标定的。E4 换上 bge-m3 后，纯向量
  Hit@5 已经是 20/20，沿用 3:1 反而降到 18/20——模型更强，融合结果更差。
- **取舍**：`MsdsRetrievalProperties` 保留 `literal-weight=3.0 / vector-weight=1.0`
  作为本地哈希档，新增 `semantic-literal-weight=1.0 / semantic-vector-weight=2.0`
  作为语义模型档；`MsdsSearchService` 每次检索时按
  `MsdsVectorService#usesSemanticEmbedding()` 选档。
- **为什么不用「模型名白名单」**：模型名是配置项，可以写成任意字符串；用
  `instanceof HashingEmbeddingClient` 判断「是否还有外部调用」，语义更准确，
  也不会因为换本地模型厂商而漏配。
- **为什么两档都保留完整配置项**：显式配置优先于默认值，运维可以直接调某一档
  而不影响另一档；如果只做一个自动比例，反而无法覆盖「同一模型在别的语料上
  最优权重不同」的情况。
- **验证**：`MsdsWeightProfileTest` 锁定两档默认值与客户端识别；
  `MsdsSemanticWeightTest` 让向量路为空、只看字面分数，断言第一名是
  `1/(10+1)`——退回 3:1 会得到 `3/11`，测试立即失败。
- **边界**：权重只影响排序，不改变候选集；`min-score` 仍需按模型重新标定，
  不属于这次改动。
- **来源**：`MsdsRetrievalProperties`、`MsdsSearchService#fuse`、
  `MsdsVectorService#usesSemanticEmbedding`、`application.properties`。

### 26. 禁忌混放按「在库 + 同柜」判断，未覆盖单独成字段（2026-11-05）

- **问题**：混放是物理存放问题。如果按「档案表里所有试剂」两两比对，已经用完、
  柜子里没有实物的试剂也会产生冲突提示；如果只看规则不看柜位，分柜存放的
  禁忌试剂也会被报成违规；如果只把冲突放进一个列表，
  「没有规则」与「确认安全」在接口上就无法区分。
- **取舍一：按 `availableQuantity > 0` 筛在库试剂**，不按有效期筛。已过期但瓶里
  还有东西的批次仍然占着柜子，仍然是混放风险；是否出库是另一条规则。
- **取舍二：关系键用 CAS 对，不用 `chemical_id`**。禁忌是化学性质，不随档案记录
  增删而改变；关系表可以独立于业务档案维护。存入时按字典序归一化，配合
  `CHECK (cas_a < cas_b)` 与唯一索引，正反序只可能有一条。
- **取舍三：`conflicts` 与 `uncovered` 分成两个字段**。`uncovered` 只代表规则表
  没有记录，不代表安全。测试用「硫酸 + 过氧化氢」锁住：这一对实际危险，
  但当前 18 份 MSDS 的第 10 节没有直接禁配表述，所以必须落在未覆盖里，
  不能被当成「检查通过」。
- **取舍四：柜位取在库批次的 `location` 交集，规则命中 ≠ 混放**。第一版只比对
  试剂级关系，种子数据里 18 种试剂分散在 13 个柜位，51 条规则命中全部是跨柜的，
  接口会报出 51 条假违规。改成：`sharedLocations` 非空才是 `conflicts`；命中但
  分柜的进 `separatedConflicts`；同一种试剂多个批次分放多处时按任一柜位相交计算。
  报告同时给出 `coStoredPairCount` 与 `coStoredUncoveredCount`，让「同柜但没规则」
  的组合排在最前面。代价是柜位只是自由文本，拼写不一致会漏报，且不区分柜内层板。
- **为什么规则种子与试剂种子分开**：`SeedRunner` 只在空库时灌档案；规则表可能
  在已有档案的库里独立补齐。两者生命周期不同，塞进同一个「库里有档案就跳过」
  的分支，会让升级后的库永远没有规则。
- **代价**：当前只有 51 对规则、覆盖种子里的 18 种试剂；还没有按 GB 15603
  条款号建完整关系。接口返回无冲突只说明「已知规则里无冲突」。
- **验证**：`IncompatibilityTest`（7 条接口行为，含同柜/分柜/未覆盖三分类与
  多柜位求交集）、`ChemicalIncompatibilityTest`（正反序归一化、自对/空值拒绝）、
  `IncompatibilitySeedDataTest`（51 条规则的 CAS 拼写、重复对、出处字段）。
  全量 `Tests run: 163, Failures: 0, Errors: 0, Skipped: 1`，`BUILD SUCCESS`。
- **来源**：`V6__chemical_incompatibility.sql`、`IncompatibilityService`、
  `IncompatibilityController`、`seed/incompatibilities.json`、
  `IncompatibilitySeedRunner`。

### 27. 生成式回答只允许引用「模型实际看到的片段」，无依据就拒答（2026-11-06）

- **问题**：生成式回答最危险的不是答错，而是答得通顺但出处无法核对。3B 模型可能
  输出不存在的条目编号，也可能在片段没有覆盖时硬编一段；用户看到 `[3]` 会以为
  真的有第 3 条依据。
- **取舍一：引用由后端生成，模型只输出编号。** 校验范围必须是「实际喂给模型的片段数」
  （`ChatAnswerClient.MAX_HITS=5`），而不是 `hits.size()`。`topK` 允许到 20，
  如果按 20 校验，模型输出一个它根本没见过的 `[9]` 也会被接受，引用就指到了另一块。
  越界编号、重复编号、零有效引用，一律整段作废退回抽取式。
- **取舍二：抽取式只在有词面依据时作答。** 本地哈希向量对任何查询都会返回噪声命中，
  第一版把「首选块第一句」兜底摘出来，结果「量子计算机怎么修」被回答成
  「中文名称：高锰酸钾」。改为：句子必须与问题（含同义词扩展）有双字重合，
  或落在问题意图对应的章节；两者都没有就返回 `answerable=false`，
  提示「片段与问题没有直接对应」。宁可说不知道，不把无关原文包装成答案。
- **取舍三：意图章节优先，全局排序选句。** 问「误食 甲醇」时，毒理块排第 1，
  按命中顺序取句会让它的两条先占满 3 个名额，真正含急救措施的 §4 排第 3 却轮不到。
  改为全局排序：意图章节（误食→§4、着火→§5、泄漏→§6……）优先，再按句内重合度，
  每块最多 2 句、全答案最多 3 句。章节标题行（`[甲醇] §4 急救措施`）不是可引用内容，
  直接跳过。代价是映射绑定 MSDS 的 16 节结构，接入国标/SOP 时要按 `doc_type` 另配。
- **取舍四：`chat-enabled` 与 `enabled` 分开。** 「算向量」和「把正文发给生成模型」
  是两种数据出境行为，不能一个开关顺带打开。默认共用 `base-url` / `api-key`；
  两者不同源时用 `chat-base-url` / `chat-api-key` 单独指向。E9 就是这种组合：
  本机 bge-m3 算向量、在线 DeepSeek 做生成。DeepSeek 没有 embeddings 接口，
  若把全局 `base-url` 指过去，288 块编码会直接失败。
- **取舍五：拒答判定锚定回答开头，宾语不限于「内容」。** 真实模型拒答时不会逐字
  复述固定句，常写「当前 MSDS 中没有找到任何关于治疗头痛的内容」并附带相邻章节引用。
  第一版按「包含拒答句」判定，又把「酸溅到眼睛应立即冲洗 [1]。其他酸类在当前
  MSDS 中没有找到相关内容。」这种有效回答整段丢掉。改为开头锚定正则：只有
  回答以「（当前）MSDS/片段……没有/未找到……」开头才判拒答；正文末尾的补充说明
  不影响可答性。E9 的库外题集又暴露第三层：宾语是「数值」「地址」时漏判
  （「没有找到甲醇口服 LD50 的具体数值」），接口会返回 `answerable=true`。
  现在宾语扩到 内容/数值/信息/资料/说明/条目/字段/地址/电话/价格/库存/数据，
  并用负向前瞻排除「没有找到 X，但 §9 给出 Y」这种同一句里把答案补上的回答。
- **代价**：抽取式仍可能在同一节里选到次要句子（例如问「闪点」时附一句外观性状）；
  模型「合法引用」的内容是否忠实于原文仍未验证——引用校验只保证编号存在且来自
  本次片段，不保证转述没有偏差。E9 只测到「引用章节对得上」，没测「句子转述对不对」。
- **验证**：新增 25 条测试（`MsdsAskTest` 3、`MsdsAnswerServiceTest` 4、
  `MsdsAnswerGenerationTest` 10、`OpenAiChatAnswerClientTest` 8），
  全量 `Tests run: 189, Failures: 0, Errors: 0, Skipped: 2`，`BUILD SUCCESS`；
  跳过的是 `MsdsEmbeddingCompareTest`（E4）与 `MsdsGenerationEvalTest`（E9）。
  E9 显式执行结果见下方 2026-11-06 实测记录。
- **来源**：`MsdsAnswerService`、`MsdsAnswer`、`MsdsCitation`、

### 28. 撤销用版本号比对，管理接口主动清缓存（2026-11-06）

- **问题**：JWT 是无状态的，停用账号、改密、改角色之后，已签发的 token 在 8 小时
  有效期内仍然可用。这在演示环境看不出来，在上线评审里是硬伤。
- **取舍：版本号而不是黑名单。** 黑名单按 token 存条目，条目数随登录量增长，还要处理
  「黑名单比 token 活得更久」的清理；版本号是每用户一个整数，存量恒定，并且天然支持
  「一键让所有设备下线」。代价是校验要读一次库——加 30 秒本地缓存后摊薄到可忽略，
  代价换成「多实例下最迟 30 秒生效」。单实例部署时管理接口改完主动 `evict`，是即时的，
  文档里把这句写清楚，不能含混成「立即生效」。
- **坑一：过滤器顺序。** `TokenVersionFilter` 必须挂在 `BearerTokenAuthenticationFilter`
  之后，否则 SecurityContext 还是空的，过滤器等于没写。
- **坑二：缓存里要存「用户不存在」。** 只缓存有效版本的话，伪造 subject 的 token 每次
  都会绕过缓存打库；把 `null` 也缓存起来，键数量由用户数封顶。
- **坑三：测试里缓存跨用例残留。** 上一个用例把 alice 停用后缓存里是「不存在」，
  下一个用例重建了 alice，缓存还不知道，断言随机 401。测试的 `@BeforeEach` 里显式 `evict`。
- **顺带补的两道门**：最后一个启用中的 ADMIN 不能被停用或降级（否则没人能再进管理接口，
  只能改库）；prod profile 下仍开着演示账号或种子数据时直接拒绝启动——这类配置一旦
  带上生产库就是可登录的后门，靠「记得改」不如靠「改了就起不来」。
- **验证**：`UserAdminIntegrationTest` 7 条（停用/改密/重置密码后旧 token 401、
  logout-all、非 ADMIN 403、最后一个管理员保护、Prometheus 端点），
  `ProductionSafetyCheckTest` 5 条。
- **来源**：`V8__user_token_version.sql`、`TokenVersionFilter`、`TokenVersionService`、
  `AuthController`、`UserAdminService`、`UserAdminController`、`ProductionSafetyCheck`。

### 29. pgvector 只做第二个 DataSource，写入顺序固定「先 MySQL 后 pg」（2026-11-06）

- **为什么不是第二个 JPA EMF**：JPA 自动配置看到第二个 `DataSource` Bean 就会歧义，
  要么加 `@Primary`、要么改变主库连接；而「同一事务写两个库」本来也做不到。
  所以 `PgVectorStore` 自己持有 Hikari 池，只对外暴露 `VectorStore` 一个角色，
  `@ConditionalOnProperty(hazmat.vector.store=pgvector)` 条件装配，默认不加载。
- **写入顺序**：`saveAll` MySQL → `upsert` pg。反过来的话，pg 写成功而 MySQL 回滚会留下
  「向量库有、台账没有」的幻影行，检索回表取不到正文，表现为静默少结果。
- **pg 失败不判编码失败**：向量是派生数据，MySQL 已落库就够了。若把 pg 异常算进编码失败，
  一次 pg 抖动会累加 `encode_failures`、触发 `max-consecutive-failures` 暂停整个编码队列，
  故障范围从「向量路降级」放大到「索引停更」。正确做法是记 `msds.vector.store.write` 指标，
  由 `reconcile()` 按 MySQL 已编码集合补写；`/status` 的 `missingRows` 暴露缺口。
- **可用性**：Hikari `initializationFailTimeout(-1)` 允许延迟建连，pg 没起来应用照常启动；
  `available()` 带 5 秒缓存探活，检索失败返回空结果并置 `degraded`，字面路不受影响。
  索引被整体停用（四元组不符）时 `suspended=true`，与内存实现「索引清空」语义对齐。
- **维度校验**：写入前校验 `float[]` 长度与 `hazmat.vector.pg.dimension`，不符直接抛错并给出
  可操作提示。本地哈希是 512 维、bge-m3 是 1024 维，静默跳过会让「向量库少了一批」变成
  难排查的静默问题；拒绝写入才能把「模型/维度不一致」暴露在编码阶段。
- **验证**：`PgVectorStoreTest` 6 条（建表/upsert 覆盖/过滤下推/按版本删除/维度拒绝/断连降级），
  `HAZMAT_PGVECTOR=true` 对真实容器跑，默认跳过。全量 `Tests run: 209, Failures: 0, Errors: 0, Skipped: 8`。
- **来源**：`PgVectorStore`、`PgVectorStoreConfig`、`PgVectorProperties`、`VectorStore#existingIds`、
  `MsdsVectorService#syncToVectorStore` / `#reconcile`、`MsdsController#reconcile`、
  `hazmat.vector.pg.*` 配置、`compose.yaml` 的 pgvector profile。

### 30. 版本化重建：写新版本、切指针、只留两版（2026-11-06）

- **问题**：原来的重建是「读旧块 → 删 stale → 插新块」，事务虽然包在锁里，但删除和插入对读方
  不是原子的。字面索引如果在提交前重建，或者查询正好落在两次提交之间，就会读到缺块的索引；
  多实例下更没法保证每个实例的视图一致。
- **为什么不是原地覆盖或双表**：原地覆盖解决不了「读方看到中间状态」；双表要么改所有查询的表名，
  要么在应用层做路由，切换瞬间仍要锁。在块上加 `index_version`、全局只维护一个 `active_version`
  指针，等价于「一次原子写指针」，读方按版本过滤即可，不需要双表也不需要分布式锁。
- **行复制而不是移动**：新版本写全新行、旧版本原样保留。移动（改 `index_version`）会让「读旧版本」
  的请求在移动过程中看到行消失；复制多一份存储，但换来了切换的原子性和回滚能力。`textHash`
  与四元组都没变时把旧向量和 `indexed_at` 一起复制过去，增量复用的语义没有丢。
- **台账没有 `BUILDING`**：原计划设计了 BUILDING 状态，实现时发现新块在单个事务里写完才切指针，
  外部永远看不到半成品，台账里放一个永远不会被读到的状态只会增加分支。最终只有
  `ACTIVE` / `PREVIOUS` / `RETIRED`，重建失败时事务回滚，指针和台账都不变。
- **只留 active + previous**：每次重建都在同一事务里删掉更早的版本，存储最多两倍。回滚因此只能
  退一版——这是有意的最小方案，多版本保留要配定期清理任务，当前没有这个需求。
- **最容易漏的是读取路径**：字面索引构建、`encodePending` 取待编码块、`status` 计数、pg 对账
  原来都 `findAll()`。任何一处漏掉版本过滤，行为会变成「新旧块各算一遍」。统一收进
  `MsdsVectorService#activeChunks()` 与 `MsdsIndexService#activeChunks()`，测试用
  「旧版本块仍存在但不出现在字面索引里」锁定这条边界。
- **回滚在锁内做，且用 `TransactionTemplate`**：交换指针和改台账必须一起成功；没有 previous 时
  抛业务异常，不返回 `200 + 什么都没做`。
- **验证**：`MsdsIndexVersionTest` 1 条覆盖完整生命周期（初次无回滚目标 → 重建 → 台账 ACTIVE/PREVIOUS
  → 回滚换指针 → 检索仍可读）；`MsdsSearchTest` 断言并发重建后库里恰好是两版块；
  E8（`HAZMAT_E8=true`）3 次重建 + 4 线程 6098 次查询，异常 0、空结果 0。
  全量 `Tests run: 211, Failures: 0, Errors: 0, Skipped: 9`。
- **来源**：`V9__index_version.sql`、`MsdsIndexVersion`、`MsdsIndexVersionRepository`、
  `MsdsIndexService#doRebuild` / `#rollback` / `#activeChunks`、`MsdsVectorService#activeChunks`、

### 31. 禁忌依据必须结构化，且「有依据 / 待核 / 无依据 / 未覆盖」四态分开（2026-11-06）

- **问题**：原来的 51 条规则只有一句 `source` 文本（如 `MSDS 1310-73-2 §10`），
  接口没法回答「这条冲突的依据是什么、核没核实」。报告里 `conflicts` 与 `uncovered` 已经分开，
  但「有规则、依据没核」这一态没有位置，只能混在 `conflicts` 里假装同等可信。
- **做法**：`V10` 加 `source_type`、`source_doc`、`source_clause`、`source_excerpt`、
  `verification_status` 五列；`IncompatibilityView` 增加 `basis`，报告增加
  `basisCoverage{total,verified,pending,missing,verifiedRatio}`。
- **三态的定义写在实体注释里**（`VerificationStatus`）：`VERIFIED` = 有出处且核对过；
  `PENDING` = 规则存在但依据未核；`missing` = 连文档字段都没有。
  **`uncovered` 不属于这三态**：它是「规则表里没有这一对」，语义是「没有依据 ≠ 安全」，
  不能塞进覆盖率的分母里稀释。
- **不编条款号**：51 对全部回填仓库内 MSDS §10 的原文摘录（脚本从 `禁配物` 行生成，
  最长 97 字），标 `VERIFIED`；GB 15603 没有授权全文，一条条款号都没有造，
  宁可让 `source_type=GB` 的位置空着。
- **种子对老库的兼容**：`IncompatibilitySeedRunner` 不再「已存在就跳过」，而是按 CAS 对
  回填依据；只填空字段、不覆盖人工改过的值，升级后老数据也能补齐。
- **验证**：`IncompatibilityTest` 用三条处于三态的规则断言覆盖率（1/3 = 0.33）；
  `IncompatibilitySeedDataTest` 断言每条种子的依据字段完整。
- **来源**：`V10__incompatibility_basis.sql`、`entity/VerificationStatus`、`dto/RuleBasis`、
  `dto/BasisCoverage`、`IncompatibilitySeedRunner`。

### 32. MySQL 的 `CHECK` 失败不是唯一键冲突，异常翻译不能一把抓（2026-11-06）

- **问题**：`CHECK (cas_a < cas_b)` 在 H2 上抛 `DataIntegrityViolationException`，
  在 MySQL 8.4 上抛 `UncategorizedSQLException`（SQLState `HY000`，错误码 3819）。
  Spring 的异常翻译只覆盖已知错误码，CHECK 不在其中。
- **影响**：如果按「捕获 `DataIntegrityViolationException` 就算约束冲突」写业务逻辑，
  换到 MySQL 后这条分支永远不触发，约束失败会落到兜底的 500。
- **做法**：测试按 `DataAccessException` + 消息包含约束名 `ck_incompatibility_order` 断言，
  不假装两种库抛同一种异常。应用层没有把 CHECK 当业务分支使用——反序插入只可能来自
  程序 bug 或手工 SQL，返回 500 并记日志是合理的；面向用户的规则校验在服务层先做。
- **顺带记录**：Docker 29 的 API 版本是 1.44，高于 Testcontainers 1.21.3 依赖的 docker-java
  默认版本，连接会报 `Status 400`；运行时加 `-Dapi.version=1.44`，不要把它写死在 pom 里
  （旧版 Docker 不认这个参数也无所谓，但别让构建依赖宿主机的 Docker 版本）。
- **来源**：`MySqlMigrationIT#incompatiblePairRejectsSameAndReversedDuplicates`。

### 33. 写路径压测要测业务链，还要断言「失败是不是可解释的」（2026-11-06）

- **问题**：只看 QPS 的压测会把所有错误平均掉。本次四条链路跑下来，表面数字都不差，
  但盘点场景 15 个 500、领用链 2 个失败，日志里是 `Duplicate entry ... for key
  'uk_stocktake_no'`——这是单号生成缺陷，不是容量问题。
- **做法**：压测器统计**状态码分布**，并把「预期内的拒绝」编码进场景定义：
  - 回滚场景以 4xx 为成功（业务拒绝），2xx 说明本该失败的链路成功了；
  - 盘点场景的 400 是「批次已在未完成盘点单里」的业务互斥，与 5xx 分开看；
  - 先查错误样例与状态码，再看延迟分位数。
- **踩到的坑（回滚场景选错入口）**：一开始用「领用量远大于库存」测事务回滚，结果 0 次拒绝。
  `StockService.issue` 对库存不足的语义是**部分出库**，超量申请会成功发出剩余量。
  回滚要用报废超量触发 `deduct` 返回 0，才真的抛业务异常、整事务回滚。
- **验证**：修复后复跑，盘点 4 并发 `400=226 / 500=0`，领用 0 失败，回滚 `400×4684`。
- **来源**：`tools/bench/WritePathBench.java`、`docs/实验记录.md` §1.9。
